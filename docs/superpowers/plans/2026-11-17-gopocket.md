# GoPocket Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A standalone Node/TypeScript bot that reads NIFTY option calls from WhatsApp, turns each into a bracket (limit + target + stop) order, and places it on web.gopocket.in with a headless Playwright browser. Buy only: the bracket order's own target and stop handle the exit, so exit messages are ignored (owner's decision 2026-11-17).

**Architecture:** One process: whatsapp-web.js client -> whitelist -> dedupe -> parse (regex first, `claude -p` fallback) -> validate -> size -> Playwright order module -> console/log outcome. Pure logic (parsing, sizing, validation, dedupe, expiry) is separate from the browser module so it is unit-tested without a browser. The browser module is verified by a headless probe that never clicks Buy.

**Tech Stack:** Node 22, TypeScript (ESM, NodeNext), whatsapp-web.js, Playwright (Chromium), vitest, tsx. Claude via the `claude` CLI (`claude -p`).

**Spec:** `docs/superpowers/specs/2026-11-17-gopocket-design.md`. Site facts (selectors, flows): `docs/gopocket-site-notes.md`. Source project to clone from: `/home/karthikeyan/later/whatsapp/` (leave it untouched).

## Global Constraints

- Project root `/home/karthikeyan/work/gopocket`, its own git repo, standalone (no imports from `/home/karthikeyan/work/icici`).
- NIFTY only; every other instrument, and chatter, is ignored (no order, no Claude call when the regex already identified another instrument).
- Every order is a bracket: Cover tab, Limit, Stoploss and Target both set. Target/stop come from the message; each missing one comes from config as percent (wins) or points.
- Site wants Stoploss and Target as the DIFFERENCE from the entry price, rounded to tick 0.05 (buy at 54, stop 41, target 68 -> stoploss 13, target 14).
- First target is used when a message has several targets (default, owner has not objected: `68-80-100` -> 68).
- Message lot size is ignored. `lots = floor(investment / price / lotSize)`; 0 lots = skip.
- No WhatsApp replies; console + `logs/messages.log` only. The bot never sends a WhatsApp message.
- Claude only extracts fields from text; it never decides to trade. Every parsed signal (regex or Claude) goes through `validateSignal`.
- Unconfirmed order outcome is reported as `unknown`, never assumed placed or not placed. Never click the site's "Repeat" button.
- Claude (the agent implementing this) must NEVER click Buy in a live account. Live orders are placed only by the owner or by the bot run by the owner. Verification uses the probe (stops before Buy) and `dryRun: true`.
- Commit messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.

## Review Focus

1. Same WhatsApp message delivered/edited twice, or two messages for the same contract within the window -> one order only (Task 5, pipeline test).
2. BANKNIFTY / stock / chatter message -> no order, and no Claude call when the regex already saw another instrument (Task 8).
3. Claude returns a plausible but wrong value (strike 2540, price 5400, stop above entry) -> `validateSignal` rejects, no order (Task 4).
4. `claude` CLI fails, times out, or returns non-JSON -> message skipped and logged, bot keeps running (Task 7).
5. Price so high that 1 lot exceeds the investment -> 0 lots, skipped (Task 3).
6. Session expired or risk-notice modal present/absent -> no order attempted on a logged-out page; notice dismissed only if shown (Task 10).

### Task 7: Claude fallback parser

**Files:** Create `src/claudeParser.ts`; Test `test/claudeParser.test.ts`.

**Interfaces:**
- Consumes `Signal`.
- Produces `type ClaudeRunner = (prompt: string) => Promise<string>` (returns the CLI's stdout), `defaultRunner(model?: string): ClaudeRunner`, `parseWithClaude(text: string, run: ClaudeRunner): Promise<Signal | null>`; throws `ClaudeParseError` for a non-JSON/ill-shaped output.
- `defaultRunner` spawns `claude -p <prompt> --output-format json --no-session-persistence --tools "" --setting-sources "" --json-schema <schema>` (+ `--model` when set), 60 s timeout. Verified 2026-11-17: the CLI's stdout is one JSON object whose `structured_output` field holds the result; one call took about 4 s, about $0.016.
- Schema fields: `relevant` (boolean, required), `instrument` (string), `action` (`buy`|`exit`; `exit` -> `null`, not handled), `right` (`CE`|`PE`), `strike` (number), `expiry` (`YYYY-MM-DD`, only when the message states a date), `price`, `stop`, `targets` (number[]). The prompt tells Claude: fix typos in the instrument name, ignore emoji and the message's lot size, prices written `41:00` mean 41.00, `relevant` is false for anything that is not a NIFTY index option call, and it must not invent missing fields. Returns the first target as `Signal.target`. `relevant:false`, instrument other than NIFTY, `action:'exit'`, or a missing strike/right/price -> `null`.
- Every call appends `{input, output, ms}` to `logs/claude-parse.log` (for later prompt tuning).

### Task 8: Signal parsing pipeline (regex first, Claude second)

**Files:** Create `src/parseSignal.ts`; Test `test/parseSignal.test.ts`; Modify `src/parser.ts` only if needed to export a helper (do not change its behaviour).

**Interfaces:**
- Consumes `parseMessage` (copied regex parser, returns `TradeMessage | null` with string fields), `parseWithClaude`, `ClaudeRunner`.
- Produces `parseSignal(text: string, run: ClaudeRunner): Promise<{ signal: Signal; via: 'regex'|'claude' } | { signal: null; reason: string }>`.
- Rules: (1) if the regex finds an instrument other than NIFTY -> `{signal:null, reason:'not NIFTY'}`, no Claude call; (2) if the regex yields NIFTY with price, stop AND target -> use it (`via:'regex'`; convert strings to numbers, `call`->`CE`, `put`->`PE`); (3) an exit/sell/book/close message (regex `action === 'exit'`) -> `{signal:null, reason:'exit messages are not handled'}`, no Claude call; (4) otherwise, if the text `looksLikeSignal` (contains a CE/PE/CALL/PUT token and a number) -> Claude; else `{signal:null, reason:'not a signal'}`, no Claude call. A regex result missing the stop or target must go to Claude, because a message-supplied stop must never be silently replaced by the config default.
- Claude errors are caught here and returned as `{signal:null, reason:'claude failed: <message>'}`.

- [ ] **Step 1:** Tests with a counting fake runner: `Nifty 23400 ce Cmp 120 target 150 sl 100` -> via regex, 0 runner calls; the sample message -> via claude, 1 call; `Banknifty 45000 CE cmp 180 target 200 sl 150` -> null, 0 calls (Review Focus 2); `good morning everyone` -> null, 0 calls; `Nifty 23400 ce Cmp 120` (no stop/target) -> 1 Claude call; `Exit Nifty 23400 ce @ 150` -> null with reason matching /exit/, 0 calls; runner rejects -> reason starts with `claude failed`.
