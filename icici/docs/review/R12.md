## Findings

### 1. Beginner can use Search & Buy by omitting `contract` (level-gate bypass) - HIGH
- `gateBuy` blocks a Beginner only when `contract` is present (levelGate.ts:16). `/order/buy` also accepts `strikePrice`, `right` and `index` (trading.ts:54,82-90; validator allows NIFTY/SENSEX/BANKNIFTY/FINNIFTY, trading.ts:40).
- `manualBuyOnKite` honours `strikePrice` first: any strike on any allowed index is bought (kiteExecutor.ts:334-342; same family on ANT/Breeze).
- Scenario: a Beginner (never approved) calls `POST /order/buy?right=call&strikePrice=26500&index=SENSEX` and trades any strike/index. Table and legal text say Search & Buy is not available to Beginners (levelTable.ts:125, legalPdf.ts:168). The global target/stop and capital sizing still apply, so the damage is limited to strike/index choice, but the rule is the platform's main level distinction. Fix idea: for non-admin Beginner reject `strikePrice` and any `index` other than the Flash Trade default.

### 2. Advanced `targetPoints=0` on a buy silently drops BOTH target and stop - HIGH
- Validator accepts `targetPoints >= 0` (trading.ts:33-35). `gateBuy` for Advanced only rewrites a stop of 0 (levelGate.ts:15); a target of 0 passes through (trading.ts:88).
- Executors arm exits only when both are positive: `targetPoints > 0 && stopLossPoints > 0` (kiteExecutor.ts:123; antExecutor.ts:221,329). With target 0 and stop 50, no stop-loss, no GTT, no bracket is placed.
- Scenario: Advanced user (or the UI sending 0 for "no target") buys with no stop at all. Sizing assumed the stop (bookkeeping.ts:404-409), so the per-trade loss cap is void and nothing but the daily drawdown breach exits the trade. Fix idea: treat 0/blank target like the stop (fall back to the global value) in gateBuy.

### 3. Per-trade loss cap can be bypassed three ways - MEDIUM
(a) Post-entry widening: `gateSetTarget` only requires stop > 0 (levelGate.ts:31); sizing happens only at buy (bookkeeping.ts:404-411). Buy with a tight stop (many lots), then `POST /order/settarget` with stop 5000.
(b) Lot-count mode: `resolveManualBuyQuantity` returns one lot before the loss-cap code (bookkeeping.ts:385), and an Advanced user may switch to lotCount themselves (users.ts:186-205, gateSettings allows Advanced). One lot with a wide stop can exceed the cap (for example 400 points x 65 = 26,000 vs 20,000 cap on 200k).
(c) One-lot floor (`Math.max(1, ...)`, bookkeeping.ts:397,411) lets a buy exceed per-order cap and capital by up to one lot (documented, but legal text 3.6 says "may not lose more than").
levelTable.ts:126 ("up to the per-trade loss cap") and legalPdf.ts:163 are therefore not guaranteed by code.

### 4. Concurrent manual buys over-commit capital; 3-per-day cap is check-then-act - MEDIUM
- `/order/buy` passes no quantity, so `estimatedValue` is undefined (orderProcess.ts:840) and `markPending` stores 0 (bookkeeping.ts:493). Sizing runs inside `place()` after the reservation and reads `pendingValue` (bookkeeping.ts:391), which is 0.
- Scenario: double-click / two tabs / scripted parallel calls: each sizes against the full free capital, so N requests commit about N x capital (user's `accountCapital` limit exceeded; only the next `canPlaceOrder` after fills sees it).
- The 3-trades/day check (trading.ts:70-81) reads `stats()` (booked trades only, not in-flight orders) and is not atomic, so parallel requests all pass it. The route also pulls every user's and strategy's open and closed trades over IPC per buy (performance).

### 5. Act-as: no audit, no write restriction, and it is the only trader path - MEDIUM
- Traders cannot sign in (auth.ts:320), so every trader action in production comes through act-as. `resolveActingAdmin` (session.ts:92, "also the hook for the Audit feature") is called nowhere except a test; `authenticate` returns `actingAdmin` that no route uses.
- While acting-as an admin can: accept legal/Advanced terms for the trader (`acceptTerms` levels.ts:199; `acceptAdvancedTerms` users.ts:332-337), change bank/UPI and KYC numbers (users.ts:278-307), upload documents (users.ts:445), place and square off orders. Records show the trader as the actor; nothing records the admin.
- Scenario: a disputed acceptance or payout destination change cannot be attributed. Fix idea: log `{admin, target, method, path}` for every non-GET while acting-as and store `by` on acceptance/bank changes; refuse terms acceptance and bank edits under act-as.

### 6. GSTIN self-upgrade to permanent Advanced uses an unvalidated string - MEDIUM
- GSTIN is checked only as `^[0-9A-Z]{15}$` (user.ts:431); no state code, PAN embedding or checksum, and `gstVerified` stays false (user.ts:433). A user sets `entityType: 'company'` themselves (users.ts:309-323; locked only after a paid payout, user.ts:414-421), then sends any 15-character string with `acceptAdvancedTerms: true`.
- `gstinUpgradeDecision` returns `upgrade` (levelUpgrade.ts:119-126) and `applyAdvanced` runs at once (users.ts:336-341): Search & Buy, own stops, capital doubled to 200,000 (levelDefaultsFor), no admin approval. The invoice rule is the only counter-measure and runs after the fact.
- Fix idea: require a checksum-valid GSTIN at minimum, or hold the upgrade until `gstVerified`.

### 7. Open SSE streams are never re-authorised - MEDIUM
- `/positionstream` and `/notificationstream` bind the user once at connect (streams.ts:247-254,306-310). Logout/revocation, disable, account deletion, role change and act-as stop do not close them; there is no timer or per-push session check.
- Scenario: a copied cookie holder keeps a live stream (positions, P&L, notifications) after the owner logs out; an admin's tab keeps receiving the target trader's positions after act-as stop; a deleted account's connection stays registered. Also no per-user connection cap on authenticated streams (streams.ts:79-85,247,306).

### 8. Admin-forced Advanced records a fabricated "accepted terms" - MEDIUM
- Settings route with `proficiencyLevel:'advanced'` calls `applyAdvanced(email,{via:'admin'})` (users.ts:248) with no acceptance, so levelUpgrade.ts:81 stamps `{acceptedAt: now, termsSha256}` as if the trader accepted. No upgrade email or notification is sent on this path (only the decision route does, levels.ts:219-223). The trader never accepted; the record is later evidence of acceptance. Also `applyAdvanced` resets `accountCapital` to the Advanced default even if an admin had set a higher figure (levelUpgrade.ts:76-80).
- `levelToWrite` (users.ts:242) is never assigned; harmless dead code.

### 9. DRAFT wording ships in the customer terms - LOW/MEDIUM
- `ADVANCED_TERMS_TEXT[0]` begins "DRAFT FOR REVIEW: wording not yet approved by the Company" (levelTable.ts:151). It is part of the signed Advanced-Terms PDF (legalPdf.ts:101-103), the Advanced T&C (legalPdf.ts:179-181) and the accepted-terms SHA-256 (levelUpgrade.ts:19-21). Today the owner-only test redirect (config.yml:38) hides it; removing `eodEmailTestRecipient` sends an unapproved draft to users, and `ADVANCED_TERMS_VERSION` is a manual constant not bumped when text changes.

### 10. Erasure is incomplete - MEDIUM
- Not pseudonymised or deleted: `upgradeRequests` and `capitalRequests` (user email, notes, acceptance hash), see lists accountDeletion.ts:277-284. Both collections hold the erased user's email indefinitely.
- No contractor handling: `DELETE /users/:email` on a contractor email erases the user row only; `contractors`, `invites`, `agreementAcceptances`, `kycChanges` are untouched (cross-ref R13).
- In-flight window: open positions are read once (users.ts:88,125) and an order placed between that read and the user-row delete books a trade under the erased email in the order process while Mongo rows were already renamed. The order process's per-user settings cache is never cleared (bookkeeping userSettingsCache).
- Session revival: the new user document created on re-signup has no `sessionsValidAfter`, and the self-delete path does not revoke sessions first, so a cookie issued before erasure is valid again (up to 30 days) once the same email exists again (session.ts:103-106,153).

### 11. "Successful week" is farmable - LOW
- A week counts if net realized P&L > 0 and no forfeit, any size (successfulWeeks.ts:244-249). Two weeks of one-rupee profits satisfy the capital-request floor. Forfeit is evaluated against the user's CURRENT capital for past weeks (successfulWeeks.ts:258-259), so a later capital change retroactively changes historical results. Admin still decides, so low.

### 12. KYC OCR/PDF path can exhaust the frontend process - MEDIUM/LOW
- PDFs are rasterised at scale 5 with no page-dimension or pixel guard (users.ts:426); any enabled user, including Beginners, can upload a 5 MB PDF with an enormous MediaBox. The 60 s timeout is a `Promise.race` that does not cancel the job (users.ts:408-417), so it keeps burning CPU/memory while the chain moves on; queued uploads hold 5 MB buffers and their HTTP requests with no queue bound. The frontend process also serves SSE/API/auth. Multer's file-size error is not mapped (generic 500).
- Minor: a file is written to GridFS before the user row update; a deleted-in-between user leaves an orphan (users.ts:466-477).

### 13. Demo subscription leak and unthrottled helpers - LOW
- `/demo/subscribe` holds are counted globally with no lease/TTL (streams.ts:126-181): a visitor who closes the tab without the unsubscribe leaks a hold until restart; 20 leaks (`DEMO_MAX_TOKENS`) make demo subscribe return 429 for everyone. Any anonymous caller can decrement another visitor's hold (count is not per caller).
- `/demo/symbols` accepts any `symbol` (streams.ts:220-230), returns every strike of the nearest expiry and registers each token as subscribable; `/demo/resolve` and `/demo/symbols` have no rate limit (only subscribe does, streams.ts:151-154) and return `e.message` on error.

### 14. Input validation gaps - LOW
- `right` is only checked to be a string (trading.ts:37-39); anything other than `'call'` becomes a PE (kiteExecutor.ts:218,335,348).
- `index` is validated case-insensitively but passed unnormalised (trading.ts:40,83); effect of a lower-case value downstream not verified.
- `POST /users` accepts any string as email (users.ts:47-59). A `|` in an email breaks the `email|ts` and `target|admin|ts` cookie formats (session.ts:57-65,83-85).
- `/order/squareoff` and `/order/settarget` answer a bare 500 on any failure, dropping the reason (trading.ts:137-140,161-164), unlike `/order/buy`.
- `/order/contract-quote` is not level-gated and returns `e.message` of the ANT failure (trading.ts:174-194). `/strategyPnl` builds `new RegExp(?match)` from the query (admin/loopback only; an invalid pattern is a 500, trading.ts:211). Closed-trade endpoints return unbounded history (trading.ts:300,314).

### 15. Legal/welcome text and the "single source" claim do not match the code - LOW/MEDIUM
- legalPdf.ts:149,155 and welcomeEmail.ts:45 state the entire allocated capital is committed to ONE trade at a time with only one open position. No such rule exists: `canPlaceOrder` only needs capital left (bookkeeping.ts:961-966), sizing is further reduced by the loss cap (bookkeeping.ts:411), so several positions can be open.
- The Agreement says NIFTY index options only (legalPdf.ts:77) while Advanced adds SENSEX and stock options (levelTable.ts:125).
- The trade limit "3" is hardcoded in four places (trading.ts:50, levelTable.ts:129, welcomeEmail.ts:45,49, legalPdf.ts:150), and legalPdf.ts:127-176 builds level terms by hand, so levelTable is not the only source.

### 16. Session/role holes - LOW
- Removing an address from `ADMIN_EMAILS` blocks new Google logins (auth.ts:320) but neither demotes the DB role (role is set only at creation, user.ts:249) nor revokes sessions; the admin cookie keeps working for 30 days.
- A legacy `email`-only cookie has issuedAt 0 and never expires server-side; it is dropped only by a revocation (session.ts:64-67,103-106).
- `PATCH /users/:email/role` can turn a contractor into a trader (`updateUserRole`, user.ts:488-494) without revoking sessions or telling the order process (users.ts:144-174), bypassing "contractors never trade" until the next push. 15 s user cache delays disable/role effects when the invalidation is not called (session.ts:119-137).

### 17. lock-profits: in-memory mutation before write; manual buys not blocked - LOW
- `toDisable.forEach(s => s.enabled=false)` mutates the object returned by `getConfig()` before `writeConfig` (trading.ts:109-113); if the write throws, this process's config copy disagrees with the file. The comment "nothing can buy behind the lock" (trading.ts:98-103) holds for strategies only: nothing in `/order/buy`, `manualBuyOnOneBroker` or `canPlaceOrder` checks the lock state, so traders and the admin mirror can still buy.

### 18. Email pipeline - LOW
- welcomeEmail.ts:3 says "deliberately NO HTTP endpoint" yet auth.ts:333 sends it from login (reachable only for an ADMIN_EMAILS address whose DB role is not admin; effectively dead).
- Welcome/upgrade sends are fire-and-forget; on failure the claim is released and nothing retries (users.ts:340, levels.ts:222-223).
- EOD: the sent record is written after the mail goes out; if that Mongo write fails the catch marks the row failed (eodEmail.ts:297-310) and a rerun resends a duplicate.
- The test-recipient redirect is implemented per caller (welcome, upgrade, EOD, invoiceRule, contractors/email, sendPayoutPaidEmail); `sendRenderedEmail` itself has no redirect (mailer.ts:104-107), so a future caller can mail real users during test mode.
- EOD/payout emails print the full UPI id (eodEmail.ts:109) while the bank number is masked.
