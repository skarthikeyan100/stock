## Findings

Severity: high / medium / low.

**F1 (high). SEBI registration is never enforced; expiry/unverified does not block Research Analyst recommendations.**
`sebiUsable()` (src/contractors/validate.ts:30) is defined but has no caller (grep across src finds only the definition and a comment in jobs.ts:50). `submissionBlock` (store.ts:122-129) checks status and agreement version only; POST /recommendations (routes/recommendations.ts:31-53), add-more (:67-110) and the owner approval (:127-165) do not check SEBI. Yet jobs.ts:62-63 tells the owner "Recommendations are blocked until a renewed date is recorded and verified" and tells the contractor "new recommendations are blocked", and feature.md claims SEBI verification. Scenario: a Business contractor whose SEBI valid-until passed (or who was never verified; `sebi.verifiedAt` unset) submits and gets approved/traded; the contractor was told it is blocked, the owner relies on that. Also `/contractor/sebi` lets the contractor replace the record (unverified again) with no resulting block.

**F2 (medium). Forecast daily limit and one-open-window rule are check-then-insert, not atomic.**
engine.ts:142-156 reads `forecastsOfDay`, evaluates `checkSubmission`, then `insertForecast`. The only guard against parallel requests is the per-contractor limiter of 10/min (engine.ts:133). Scenario: two simultaneous POST /forecast calls both see todaysCount < dailyLimit and no open window, both insert: 2 open windows, or dailyLimit+1 forecasts; each correct one earns a fee (statements.ts:85-87). No unique index or CAS exists on forecasts.

**F3 (medium). "Reopen on receipt" has no implementation.**
invoiceRule.ts:3 and levelTable.ts:51 say the account is reopened when the invoice arrives. The only code touching `accountClosed` to false does not exist (grep: `closeUserAccount` only; nothing sets `accountClosed: false`; `updateUserSettings` has no such field). `POST /admin/payouts/:id/invoice-received` (routes/payouts.ts:293-306) only flips `invoiceStatus` to received. Scenario: the user pays late, the account is closed by the hourly check, admin marks the invoice received, the account stays closed and the T&C promise is unmet unless Mongo is edited by hand (and the order process cache is also not refreshed since no push is made).

**F4 (medium). scripts/migrate-profit-split.js would overwrite every user's level-based split with 40.**
migrate-profit-split.js:5,13-15 sets `profitSplitPercent: 40` on all users not already 40. Current config.yml:25-32 and levelRules.ts:23-24 define beginner 35 and advanced 25, and constants.ts:17 DEFAULT_PROFIT_SPLIT_PERCENT = 35. Scenario: the script (committed under e21e440 "profit split 60/40") is run (it is idempotent and has only an optional --dry-run), all users, including Advanced and GSTIN users, are moved to 40; the next payouts pay 40% regardless of level. Past payouts keep their snapshot. Also hardcodes mongodb://localhost:27017/stocks.

**F5 (medium). Weekly/monthly statement jobs are not caught up after a missed run despite the comment.**
jobs.ts:73-79 runs statements only if the hourly tick lands on Wednesday after 06:00 (`wd === 3`) or on the 1st. The comment says "a missed hour is caught by the next", which holds only within the same day. If the frontend is down/restarting for all of Wednesday (hot restarts reset the 60 min timer, server.ts:202, no initial run), no weekly statement is made until the owner POSTs /owner/statements/run (statements.ts:74-79); the same for the monthly retainer. Fixed-period settlement does catch up (it is run from the same weekly call, so also skipped that week).

**F6 (medium). Overdue-invoice pause can be skipped permanently.**
jobs.ts:41-45 sets `invoiceFlagged: true` before it knows whether the pause applies; the pause update matches only `status: 'ACTIVE'`. If the contractor is PAUSED, AGREEMENT_PENDING, or otherwise not ACTIVE at that hour, the statement is flagged and never revisited, so when they later return to ACTIVE with the invoice still missing nothing pauses them. (The "fees are never clawed back" design is unaffected.)

**F7 (medium). Fee-model change mid-week drops or double counts days.**
statements.ts:115-117 picks the model in force on the week's last day for the whole week. PROFIT_SHARE->FIXED_PERIOD effective mid-week: the week returns null (no profit-share for the pre-change days) while the fixed period starts at `from` (:152): those pre-change days are unpaid and any loss chain stops. FIXED_PERIOD->PROFIT_SHARE effective mid-week: the week counts all trades of the week (:119) including days still covered by the fixed period (windowEnd = next `from` - 1, :150), so those trades are paid twice (once in the fixed period's net, once in the week). Also `prev` carried-forward loss (:124) is read from the last PROFIT_SHARE_WEEK statement before the week even if a fixed period lies between.

**F8 (medium). A failed invite acceptance leaves state that blocks the retry.**
invite.ts:185-198: after consuming the invite, `ensureContractorUser` (users doc, role contractor) and then `contractorsCol().insertOne` and `recordAcceptance` run in a try. On failure the invite is released and the contractor (if inserted) set TERMINATED, but the users document is not removed. The retry hits invite.ts:180 (`users.findOne({ email })` or contractor exists) and returns 409 "already registered". Needs admin cleanup.

**F9 (low). Recommendation approval edge cases.**
(a) Approve flow flips to APPROVED, then places the order (routes/recommendations.ts:144-157); if `placeContractorBuy` throws after the broker accepted the order (timeout), the record is reverted to PENDING with an unguarded update and a second approval can buy again (tradeInProgress only sees registered trades). (b) Approval has no hours/cut-off check: between 15:30 and the next hourly expiry tick (jobs.ts:26) a pending recommendation can still be approved and a resting limit buy placed. (c) Between approval and revert the contractor sees APPROVED.

**F10 (low). Recommendation submit limits are check-then-insert.** routes/recommendations.ts:43-48,: PENDING check and per-day count are read then inserted; concurrent requests can exceed `recommendationsPerDay` (config sets 3) or have two PENDING.

**F11 (low). (a) Active-contractor cap race:** invite.ts:200-203 reads `activeCount()` then updates; concurrent acceptances can exceed `maxActiveContractors`. (b) KYC-change approval (ownerContractors.ts:167-174) marks APPROVED first, then writes the contractor; a crash between loses the change while status says approved; approved values are not re-validated and PAN/GSTIN/bank can change with no re-verification step.

**F12 (low). KYC encryption hardening.** kycCrypto.ts is correct (random 12-byte IV per call, tag verified on decrypt). Gaps: no AAD binding a ciphertext to its contractor/field (someone with DB write can copy an encrypted bank account from one contractor to another and it decrypts fine); the only version marker is the `v1:` prefix with a single env key and no key id or rotation; `maskedField` (:26-29) returns `XXXX` on any decrypt error, silently hiding a wrong/rotated key; key only in .env (which is gitignored; .env.example has it blank).

**F13 (low). Session "rotation" does not invalidate the old cookie.** routes/auth.ts:87 re-issues the cookie at most daily on /auth/me; the previous signed cookie remains valid until its own `days` expiry (up to 365 days for Individuals) or until `sessionsValidAfter` is set by an admin/logout. A copied cookie is not cut by rotation.

**F14 (low). Admin/Trades P&L summary display.** (a) payout.ts:276 `weekStart.toISOString().slice(0,10)`: weekStart is local IST midnight, so the UTC date is the previous day (a Wednesday week shows Tuesday); `weekEnd` (Tuesday 23:59:59.999 IST) is shown correctly. (b) payout.ts:243 `exitTime <= to` while routes pass an exclusive end from `periodFromInputs`: a trade exactly at 00:00:00.000 IST is included in two adjacent ranges (negligible).

**F15 (low). Retainer activation day uses the UTC date.** statements.ts:101 `new Date(activatedAt).toISOString().slice(0,10)`: an activation between 00:00 and 05:30 IST counts as the previous day, adding one pro-rata day.

**F16 (low). Invoice reminder is marked sent when mail is not configured.** invoiceRule.ts:63 returns silently when mail is unconfigured, then :91-92 stamps `invoiceReminderSentAt`; the reminder never retries.

**F17 (low). Payout period/scope is not constrained by the create route.** `periodFromInputs` accepts any start/end (periodEnd may be in the future, not Wed-Tue); the weekly forfeiture is evaluated on the weeks inside the chosen period (payout.ts:123-133), so a period that omits a breaching day/week avoids forfeiture, and forfeiture-rejected records are ignored by the overlap check (payout.ts:364-369) so the same trades can be paid in a re-created narrower period. Created payouts for a period ending in the future exclude trades closing later and block those days (overlap). createPayoutRecord also does not refuse a contractor-role user (computePayout would pay profit-split on contractor trades through the user-payout path with `investmentAmount` 0, so drawdown forfeiture is skipped: `computeDrawdownForfeiture` returns unforfeited when investmentAmount <= 0, payout.ts:107). Admin-controlled, so low.

**F18 (low). Invoice HTML tax line can disagree with the tax applied for legacy rows; no GST on invoice.** payout.ts:576 uses `gstVerified !== false`, computeTax uses `gstVerified` truthy (tax.ts:16): a company payout stored without a `gstVerified` field shows "GST Registered - No TDS" though TDS was deducted. `gstAmount` is always 0 (tax.ts:19): a GST-registered company's payout invoice adds no GST (documented as reserved).

**F19 (low). Tool entry points do not pin TZ.** tools/sendEodEmails.ts, checkInvoices.ts, sendContractorEmails.ts do not import util/tz, but payout.ts week bucketing, invoice reminders, and `startOfWeek` use local time; correct on this IST host (verified `date +%Z` = IST), wrong on any non-IST host.

**F20 (low). Out-of-order statement creation breaks the monthly cap and the loss chain.** statements.ts:90 counts only earlier-start statements (`periodFrom < week.from`) and :124 only earlier PROFIT_SHARE_WEEKs. A manual run for an older week after a newer one exists computes against an incomplete history (cap can be exceeded, carry-forward understated).

**F21 (low). Tax-phase lock is bypassed for orphan statements.** statements.ts:209,217: `contractor && !contractor.isTest && !taxPhaseComplete()`; when the contractor record is null (route passes `c` null if getContractor fails) approve/pay proceeds.

**F22 (low). Zero-amount statements are payable and create an invoice duty.** `create` allows gross 0 (statements.ts:71; required so the carry-forward chain has records), so a Business statement of 0 can be approved and marked paid with an invoiceDueAt and, if not invoiced, pauses the contractor (jobs.ts:41-45).

**F23 (low). Doc/comment mismatches.** (a) invite.ts:171-172 derives the placeholder email from the GSTIN (`<gstin>@example.com`), but validate.ts:23 and the route comment say SEBI number. (b) order.ts:19 says "or one opened today" but `tradeInProgress` only checks open trades. (c) POST /owner/agreements writes both PDFs before `scheduleVersion` (ownerContractors.ts:194-197); a failure after the write leaves the version dir in place (versionAvailable then true, so the same version number cannot be reused).
