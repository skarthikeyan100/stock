## Findings

1. [MEDIUM] Momentum sets the "previous slot" reference to the CURRENT price for slots that came due before this process started. MomentumAtFixedTimeStrategy.ts:188-191 does `setSlotPrice(ltp)` where `ltp` is the tick at process start, not the slot-time price. Scenario: restart at 11:05. Slots 10:00..11:00 are all "before processStartedAt" (and not already in `keys` if the process was down), so each stores the 11:05 price. At 11:10 the move is `ltp(11:10) - ltp(11:05)`, 5 minutes, logged as "since previous slot" and compared against `minMovePoints` 10. The comparison window is shorter than the designed 10-minute slot gap, and the direction check can pass or fail on a different window than intended. NiftyChange avoids this (see finding 2) by not recording a price.

2. [MEDIUM] NiftyChange leaves a stale persisted slot price when a slot is skipped because it is before process start. NiftyChangeStrategy.ts:104-112: the `slotTime.isBefore(processStartedAt)` branch (non catch-up) does `continue` without calling `setSlotPrice`. The "Missed" branch (:113) clears it, the start-skip branch does not. `slotPrice` is persisted per day (LimitEntryStrategy.ts:228-238). Scenario: slot A 10:40 fires and records price A, process down 11:30-11:50, restarted, slot B 11:40 is skipped (before start) and keeps price A, then slot C 12:30 (in time) takes `reference = getSlotPrice()` = price A and treats it as the "previous slot" (:119-121). The move is measured over two slots (about 1h50m) and can trade. Fix idea: clear the price in that branch, as in :113.

3. [LOW, doc] HighLow "half-at-target + trail when `trailDistance` is set" is not reachable. `CandleEntryStrategy.trailDistance()` returns 0 (CandleEntryStrategy.ts:62-64, comment "no strategy turns it on today"). HighLow does not override it and reads no `trailDistance` key (grep HighLowStrategy.ts: no occurrence). Setting `trailDistance` in the block does nothing. feature.md section 6 HighLow line and nothing in config validation mention it. Only the checkpoint exit (and plain target/stop below 2 lots) is live.

4. [MEDIUM, paper today] Expiry has no loss bound and no cycle-count bound. Gates before every entry (ExpiryStrategy.ts:254-263): pending age, flat leg, EOD, target/stop set, `isGlobalMaxProfitLatched`. A stop hit always flips to the opposite right at once (expiryCycle.ts:52) and a target always re-buys. On a choppy day each stop costs about `stopLoss` x qty (config: 8 points x lots from a 100000 budget) and the loop continues until EOD. Only profit is latched. I did not verify whether `settings.maxDailyLoss` or another monitor stops it (memory notes it is unset). Own `maxProfit` relies on code outside R11; and R07's `formatPercentFields` rewriting `maxProfit: 20000` to "20000%" would make configValidation.ts:409 reject the block (it must be a number), so the strategy could fail to load after a config rewrite.

5. [LOW] Expiry drops a pending re-buy/flip older than 2 minutes and then never re-enters that broker for the day. ExpiryStrategy.ts:254 `drop(...)` clears `pending`; `maybeFirstEntry` returns when `b.seq` is set (:236), so nothing recreates it. Scenario: stop hit at 11:00 creates pending(opposite); the process hot-restarts or the order process is unresponsive for more than 2 min; the pending is dropped with an ALERT and the strategy is idle until tomorrow. Intended ("never placed late") but the consequence (no further cycling) is not stated in feature.md or the header.

6. [LOW, doc] Stale "at the option's LTP" wording. Entry limits are now the central best bid (LimitEntryStrategy.ts:581 path; Expiry's own log :274 says "limit at the best bid"; commit 7e22448). Still saying LTP: MomentumAtFixedTimeStrategy.ts:20, NextWeekStrategy.ts:16, GammaBurstStrategy.ts:21, HighLowStrategy.ts:17, ExpiryStrategy.ts:20/22, CandleEntryStrategy.ts:5, BreakoutStrategy (comments) . Operational consequence: a bid-priced limit may rest unfilled until `entryTimeoutMinutes`; for NextWeek/Breakout/HighLow/Momentum one missed candle/slot is consumed (key marked) with no retry.

7. [LOW, doc] HighLow header example `brokers: [paper]` (HighLowStrategy.ts:39) contradicts config.yml:441-442 (`kite`) and feature.md. Config is authoritative; header is stale. Likewise NextWeek/Breakout headers show `target: 20 / stopLoss: 12` but config.yml:408-421 sets neither, so both inherit `settings.target: 10` / `settings.stopLoss: 20` (config.yml:13-14): a stop twice the target. That is a config-sizing risk to confirm with the user before enabling, not a code bug.

8. [LOW] Strike choice differs by strategy and feature.md line 99 ("half-days-to-expiry OTM strike shift (`entryStrike`) for spot-index buys") applies to NiftyChange only among R11 strategies (NiftyChangeStrategy.ts:134). NextWeek/Breakout/GammaBurst/HighLow/Expiry use plain `Math.round(x/50)*50` (CandleEntryStrategy.ts:143-145, expiryCycle.ts:61-63); Momentum uses `ceil` for CE and `floor` for PE (MomentumAtFixedTimeStrategy.ts:232-233). Not a bug, but the docs imply a shared rule.

9. [LOW] Index/fut ticks are latest-wins per strategy (strategiesProcess.ts:333-338 `enqueueLatestIndex`). While `onCandleClosed` awaits an order placement or Mongo write, intermediate ticks are coalesced, so the candle built right after can miss a high/low (HighLow/GammaBurst/NextWeek candle rules depend on H/L). The candle that closed is complete; the effect is limited to the next candle during the await. Reported as an observed design trait.

10. [LOW] Momentum depth lookup always resolves contracts on broker `ant` (MomentumAtFixedTimeStrategy.ts:234, depth feed via ANT) even when `brokers: [kite]`. If ANT's session or depth feed is down, no slot trades; the failure is logged ("no order-book depth") but not alerted. Config.yml:403-406 trades on kite only.

11. [LOW] Expiry `unwatchTokenOnSource('ant', ...)` hardcodes the source (ExpiryStrategy.ts:155) regardless of the leg's broker. Whether the Kite/Breeze/Prism feed watch of a drifted leg is released was not verified.

12. [LOW] Breakout stores candle 1 in the Mongo `breakoutAnalysis` document only at candle 2 close (BreakoutStrategy.ts:175-182); a restart between 09:30 and 09:45 loses candle 1 and writes `candle1: null` (analysis only, no trading impact).

## Checked, no defect found

- Double orders: every slot/candle path marks its key (`markCycle`/`startCycle`) before the order and checks `isRunning()`; Expiry persists `seq` before `startCycle` (ExpiryStrategy.ts:266-273) and a crash between leaves a keyless cycle that `decideCycleEnd` retries (max 2).
- `enabled:false`: Breakout re-checks `enabled` (BreakoutStrategy.ts:84); Expiry's option path too (:131); the dispatcher withholds ticks from disabled strategies.
- NaN: NiftyChange `prevClose` NaN fails `reference > 0` and skips (NiftyChangeStrategy.ts:125); candle code filters non-finite ltt/ltp; HighLow signal helpers check `Number.isFinite`.
- Per-broker keying: Expiry state is per broker (`bs(broker)`, one cycle key per broker); the others fan out inside LimitEntryStrategy.
- Time windows: all use local (IST) `Date` fields; 15-min buckets align because the IST offset (19800 s) is a multiple of 900; GammaBurst/HighLow pass explicit `originSeconds`.
- YAML time quoting: config.yml keeps slot times quoted; configValidation requires HH:mm for Momentum (:348) but I did not find a NiftyChange `times` validation, so an unquoted `10:40` (sexagesimal number) would be silently dropped by `slotMoment` (NiftyChangeStrategy.ts:70-74). Not currently occurring.
