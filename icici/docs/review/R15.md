## Findings

### 1. migrate-profit-split.js would reset every user to 40 percent, contradicting the level rules - high
- scripts/migrate-profit-split.js:1-3,8,15-16: `TARGET = 40`, "matching DEFAULT_PROFIT_SPLIT_PERCENT ... platform 60%, user 40%"; it `updateMany({profitSplitPercent: {$ne: 40}}, {$set: {profitSplitPercent: 40}})` and applies unless `--dry-run` is passed. The comment is stale: `DEFAULT_PROFIT_SPLIT_PERCENT = 35` (src/constants.ts:17) and `settings.levelRules` gives beginner 35 and advanced 25 (config.yml:31,37; levelRules.ts:23-24).
- Scenario: someone re-runs the "one-off, idempotent" script (npm has no entry, but the file is in the scripts list of feature.md). Every user, including Advanced users at 25, gets 40; payout.ts:151-154 pays `grossProfit * userDoc.profitSplitPercent / 100`, so each subsequent payout overpays the user by up to 15 points of gross profit. Not reversible from the data (no previous value kept).
- Remedy (owner decides): delete the script or make `--apply` explicit and read the target from levelRules.

### 2. POST /config is a whole-file overwrite, not diff-based; it drops comments; stale admin saves revert newer edits - medium
- ConfigService.writeConfig calls `mergeIntoFile(config)` first, which only merges when `config === this.config` (ConfigService.ts:33). `POST /config` passes `configService.flatToConfig(flat)` (admin.ts:104,116), a new object, so the merge is skipped and the posted file replaces config.yml entirely. feature.md line 180 "diff-based write" is true only for strategy self-writes.
- Scenario: admin opens the config page, then Recommendation-1 (or BulkPcrAutoStart) writes `enabled: false` to config.yml at the end of its cycle (documented in strategies.md:351); admin saves an unrelated change; the stale `enabled: true` for that block is written back and the strategy re-arms. Same class as the 2026-11-02 maxInvestment revert recorded in the ConfigService comment, still open on this route.
- `dump(shaped, { noRefs: true })` (ConfigService.ts:75-80) cannot keep YAML comments; current config.yml has 0 comment lines (grep), so any operator comment added is lost on the next write by either path. The CLAUDE.md rule "never delete config.yml entries" is enforced for blocks (admin.ts:108-114 needs `?allowRemove=true`; mergeIntoFile never removes a block) but not for keys inside a block: a posted block missing a key deletes it.
- Related: configVocabulary.fill (configVocabulary.ts:11-14) lets the canonical `targetPoints`/`stopLossPoints` win over `targetPriceDiff`/`stopLossPriceDiff`; config.yml holds both (lines 4-5, 11-12). Editing only the legacy key in config.yml is silently ignored.

### 3. deploy.sh rsyncs broker credentials, the report-signing key and user storage to the server - medium

- Scenario: every deploy copies those files to ~/icici on 139.59.4.137. The passphrase is in the excluded `.env`, but broker passwords land in plaintext on the remote host, and rsync overwrites remote `storage/` copies of what the server wrote there.
- Also: the host/user/path are hard-coded (deploy.sh:6-9) and the script has no `--dry-run` or confirmation step.

### 19. Fill/tracker review of pendingAntLimitOrders.ts, fillNetting.ts, timedFills.ts - no high/medium defect found; items below
Verified correct:
- pendingAntLimitOrders: ANT-specific logic is only trade-book fill resolution and the give-up path; Mongo persistence/dedupe live in pendingOrderTracker (R06). Restart safety: `unverifiableCount`, `flatNoFillCount`, `giveUpAlerted` are in-memory by design (lines 8-20) and a restart only delays the give-up; `fromDoc` (195-204) re-hydrates the persisted fields and defaults `action` to Sell. Drop happens only for a Sell flat at the broker, after booking any trade-book fill (lines 79-103, 124), quantity-without-price throws and retries instead of booking a zero price (84-88, 184-190), five consecutive flat/no-fill polls required (30, 98). Dedupe of the booked fill is `bookkeeping.recordFill` (brokerOrderId claim before the first await, Mongo `fillAlreadyStored`, bookkeeping.ts:1112-1150), so a re-run of the fallback after a restart does not double-book.
- fillNetting: `collapseFillsByOrderId` counts one order id once (owner ledger decides across users; ambiguity returned, never guessed); FIFO and `netWithShortCover` are pure and consistent with their call sites (bookkeeping.ts:1915, 2606, 2694, 2850-2926).
- timedFills: every zone-less time is read as IST; month index NaN and out-of-range fields yield NaN then null (lines 29-32); ANT per-order average uses the last execution row (ant/tradeBook.ts) so partial chunks at different prices are not mis-averaged.
Minor, no live failure shown:
- a) `netFifoLots` (fillNetting.ts:64-82) treats every non-`'Buy'` action as a sell, while `pairFillsFifo` (:110) ignores anything that is not exactly `'Sell'`. An action spelled `SELL`/other would reduce open lots but never be paired into a closed row; today all writers use `'Buy'`/`'Sell'`.
- b) `collapseFillsByOrderId` keeps only the first doc when one user has several docs under one order id (:48-49). That relies on the invariant "one fill row per broker order id", which is enforced by `processedFillIds` in recordFill (a later partial then rest of the same order would be dropped as "redelivered", bookkeeping.ts:1121-1123). Covered by R05; noted because it makes any second same-order row an undercount at restore time.
- c) `finish()` (timedFills.ts:86-87) numbers untimed/ID-less rows `${orderId}#${idx}` with `idx` the row index in the book. ANT's book lists newest first, so a new execution prepends and shifts the index of every earlier row between polls; any consumer that dedupes by `tradeId` across two reads of the ANT or Breeze book will treat the same execution as new. foreignSells.ts only sorts and sums by `tradeId` within one read (lines 49-66), so no cross-poll dedupe exists today; the index form is unstable if one is added.
- d) `timedFillsFromKite` takes `String(r.tradingsymbol)` without checking presence; a row lacking it yields the tsym "undefined" (harmless in matching, wrong in logs).
- e) pendingAntLimitOrders `stillOpen` (lines 76-78) matches by trading symbol across the whole ANT account, so another strategy's or a manual position in the same contract keeps a flat-for-this-order Sell tracked indefinitely with only one ALERT (conservative, by design, comment 70-72).
