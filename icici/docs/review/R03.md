## Findings

### 1. HIGH: an unreadable ANT position or trade book reads as "flat" or "empty" (false external closes)

- Evidence:
  - `ANT.getPositions()` without `strict` returns `[]` for any non-Ok envelope (`ANT.ts:353-359`).
  - `ANT.getTrades()` returns `[]` for any non-Ok envelope (`ANT.ts:319-322`).
  - The authors already know ANT answers HTTP 200 with an error envelope for an invalid session (`ANT.ts:286`, `ANT.ts:912-915`).
  - `bookkeeping.readBrokerRows` calls the non-strict version (`bookkeeping.ts:1793`), as does `reconcileAntPositions` (`bookkeeping.ts:1605`).
  - The header of that reader says "a failed read must never look like everything flat" (`bookkeeping.ts:1782`). That invariant is violated for ANT.
  - `syncExternalCloses` then treats every tracked ANT lot as flat (`bookkeeping.ts:1969-2040`). The confirmation read 3 s later uses the same non-strict call and returns the same `[]`.
- Failure scenario: the ANT session is invalidated server-side (login on another device, revoked token) while `.ant_session.json` still holds today's token, so the local staleness check passes. A POST /reconcile or an order-process restart calls `syncExternalCloses(broker, 0)`. The periodic run is safer because it needs `minFlatMs` of continuous flatness. Every open ANT lot is booked as "closed outside the platform" at an implied price, removed from `trades` and unregistered from the exit monitor, and the realized P&L is fabricated. The positions are still open at the broker, now unmonitored and unprotected. The Mongo "already closed" check only stops this when Mongo already shows a Sell.
- The trade-book variant (`bookkeeping.ts:2110`, `bookkeeping.ts:2460`) is milder. An empty book means missed foreign-sell attribution and timed-fill sync, and `routes/brokers.ts:155` debug reads show "no positions" for a dead session.
- Fix direction: have `readBrokerRows` and `reconcileAntPositions` call `getPositions({ strict: true })`, and add a strict mode to `getTrades` that tolerates only the EC926 "No trades found" reply.

### 2. HIGH: an ANT or Kite placement timeout is not turned into an "order may be live" outcome (duplicate-order risk)

- Evidence:
  - `ANT.submitOrder` tags a no-response failure `ambiguousPlacement: true` (`ANT.ts:675-681`). `grep` shows the flag is read in exactly one place, `antExecutor.ts:1169`, which only logs it.
  - The order process tags `[ORDER_MAY_BE_LIVE]` only from `orderMayBeLive` or `fillStateUnknown` (`orderProcess.ts:1389-1392`).
  - `LegManager.isUnconfirmedBuyError` recognises only `[HEDGE_UNCONFIRMED]` and `[ORDER_MAY_BE_LIVE]` (`strategy/LegManager.ts:154-157`).
  - `LegBrokerOps.buy` upgrades only the text "fill status unresolved" (`strategy/LegBrokerOps.ts:70`).
  - Any other buy failure is "ordinary failure - free the slot so it can retry" (`LegManager.ts:1346`).
  - Kite has the same gap. `kc.placeOrder` timeouts and network errors propagate untagged (`Kite.ts:63-65`, `Kite.ts:264-269`).
- Failure scenario: ANT `placeorder` hits the 15 s timeout, or Kite's 7 s one, while the broker accepted the order. The error reaches ContinuousStrategy, ScaledHedged or SimpleContinuous with no tag. The slot is freed and the next tick buys again, giving two live buys and a naked or oversized leg. For sells, the same untagged failure re-sells a position that already sold.
- BulkPcr is safe (`BulkPcrStrategy.ts:113-125` matches definite refusals positively). The LegManager family is not.
- Fix direction: map `ambiguousPlacement` and Kite no-response errors to the `orderMayBeLive` flag or tag in the order process catch.

### 3. MEDIUM: NOT_PLACED is lost for ANT queue refusals, and definite refusals are inconsistently classified

- Evidence:
  - `runOrderWrite` throws `markNotPlaced(...)` when a write waited over 30 s (`util/brokerOrderQueue.ts:59-62`).
  - `ANT.submitOrder` catches every error without `e.response` and replaces it with a fresh `ambiguousPlacement` Error (`ANT.ts:675-682`). That drops the NOT_PLACED flag and the `cause`. Kite does not rewrap.
  - Other definite refusals are untagged on ANT: a 4xx response (rethrown raw at `ANT.ts:682`), a 200 body without `brokerOrderId` (`ANT.ts:687-690`), and no session (`ANT.ts:374`, thrown before any send).
  - Other definite refusals are untagged on Kite: only price-band is tagged (`Kite.ts:268`). Margin or funds `InputException`, `assertBuysNotHalted` (`Kite.ts:67-71`) and a session failure are not.
  - `placeReplacementExit` shows the intended rule (`antExecutor.ts:1068-1073`: tag a 4xx or "placeOrder failed" body), but entries and other paths do not use it.
- Failure scenario: ANT queue starvation (30 s of earlier writes) means nothing was sent, yet the strategy sees an "outcome UNKNOWN" error. BulkPcr's `isNothingBought` returns false and latches the slot in error. An explicit ANT refusal on an entry is likewise never recognised as retry-safe.
- Fix direction: rethrow errors that already carry `notPlaced` before the ambiguity rewrap, and tag 4xx and no-id bodies in `submitOrder`.

### 4. MEDIUM: a timed-out bracket or cover entry leaves a live resting order untracked

- Evidence:
  - For a bracket or cover parent, `resolveUnconfirmedAntBuy(..., mayCancel = !(useCover || useBracket))` passes false (`antExecutor.ts:308-309`) and throws "manual review" without cancelling (`antExecutor.ts:93-95`).
  - The entry is priced at the best bid rounded down (`antExecutor.ts:241`), a passive price, so a non-fill within the fill-wait window is the normal case.
  - Reachable when both points are positive and the user's `useGTT` is on (`antExecutor.ts:221`).
- Failure scenario: the BO limit rests. The wait ends. The function throws, so there is no `recordFill`, no `registerTrade` and no exit watch. The price later reaches the bid and the BO fills with broker-side legs that the platform does not know exist. Position limits and the max-profit latch are blind to it.
- Fix direction: at minimum persist the order id in the pending tracker (a buy-side pending order) so the poller books it, or cancel the BO parent.

### 5. MEDIUM: ANT market-style exits do not take the per-contract sell lock

- Evidence:
  - The `withSellLock` header says every sell placement, limit or market, runs under it (`BrokerExecutor.ts:5-11`).
  - It is applied only to `squareOffLimit` and the bare limit-sell IPC (`brokerExecutors.ts:78`, `orderProcess.ts:1056`).
  - `AntExecutor.squareOff` and `marketSell` call `squareOffOnAnt` directly (`brokerExecutors.ts:73-74`, `brokerExecutors.ts:84`).
  - `placeLimitSellBareOnAnt` (`antExecutor.ts:744-763`) only becomes visible to the resting-sell count at `trackPendingAntLimitOrder` (line 761).
  - `squareOffOnAnt` reads `pendingAntSellsFor` (line 1100), passes `restingSellQuantity: 0` (line 1154) and sizes from the live position only.
- Failure scenario: this is the 2026-11-16 incident class (target sell in flight, second full-quantity sell). A target limit sell is mid-placement (after `placeOrder`, before tracking). A stop-loss or max-profit exit calls `squareOffOnAnt`, sees no resting sell and a full live position, and sells too. Both fill, leaving a short. The reverse order also works: `placeLimitSellBareOnAnt` does not look at `pendingSquareOffs`.
- Kite is protected by its own per-contract `acquireSellLock` inside `placeLimitSellOption` (`Kite.ts:292-312`, `Kite.ts:352`).

### 6. MEDIUM: partial square-off of a bracket or cover position (and a guessed exit price)

- Evidence:
  - With `antOrderNo` set, `squareOffOnAnt` calls `exitBracketOrder`, which closes the whole bracket (`antExecutor.ts:1125-1131`).
  - It then books only `min(requested, open)` (line 1111) at `existing.lastTradePrice ?? price ?? 0` (line 1217).
  - There is no broker confirmation. The same function's comment states "never record a sale on a guessed price" (line 1194).
- Failure scenario: a manual partial square-off (quantity below the position) of a BO position closes everything at the broker but books only the partial quantity. The remainder stays "open" in bookkeeping (and counts toward limits) until a later reconcile. The booked price is the last tick, not the fill.

### 7. MEDIUM/LOW: the cancel-and-recheck helper can untrack an order whose in-flight partial fill is not yet visible

- Evidence:
  - `cancelAndRecheck` consults `terminal` only when the cancel failed (`BrokerExecutor.ts:271-281`). With a successful cancel, a recheck showing `filledQuantity = 0` goes to `untrack()` at line 280.
  - ANT's `isFilled` is a single `getOrderStatus` read right after the cancel call (`antExecutor.ts:797-800`). Kite's is a single `getOrderHistory` read (`kiteExecutor.ts:792-798`).
  - Contrast `resolveUnconfirmedAntBuy`, which waits up to 10 s for a terminal status before reading (`antExecutor.ts:117-124`).
- Failure scenario: the order partly fills at the exchange while the cancel is being processed, and the history read still shows the pre-cancel state. The helper untracks the order. The tracker, which would have booked the partial from the CANCELLED status, never sees it. A real partial position exists at the broker with no booking until a reconcile. Whether history lags the cancel is not something I could verify from the code.

### 8. MEDIUM/LOW: the Kite GTT stays live while an in-app exit sell is working

- Evidence:
  - `squareOffOnKite` never deletes or checks the GTT (`kiteExecutor.ts:458-538`).
  - The GTT is deleted only after the sell fill is booked (`bookkeeping.ts:1393-1399`, `bookkeeping.ts:1435`), through the same order queue (`Kite.ts:590`), which can be 1 s or more behind.
  - `getSellableQuantity` counts positions and open orders, not GTTs (`Kite.ts:328-344`).
- Failure scenario: a stop exit's limit (min(ltp, bid) x 0.95) fails to fill at once on a gap. Price touches the GTT stop or target trigger, and Kite places the GTT's own full-quantity SELL. Both fill and the account is short.
- The window is normally short because the 5 percent-below limit usually fills immediately.

### 9. LOW: ANT order-notify startup and liveness

- Evidence:
  - A failure of `getWsToken` inside `doConnect` throws before any socket exists, so no reconnect timer is armed (`AntOrderNotifyStream.ts:113-118`).
  - The caller only logs it and says "ANT fills will not resolve until this connects" (`orderProcess.ts:181`).
  - The stream has no inbound-silence watchdog. The market-data socket does (`AntWebSocket.ts:67-79`); this one only sends a heartbeat every 60 s (`AntOrderNotifyStream.ts:138-142`).
- Failure scenario: one transient `createWsToken` failure at startup disables push fills for the whole session. Every entry and exit falls back to REST polling (`ANT_FILL_PLAN`). A half-open socket silently stops delivering, and the foreign-sell feed (`onOrderRow`) stops with it. REST fallback keeps correctness, so this is a latency and visibility issue.
- Also: `createWsToken` response, which contains the order token, is logged in full (`AntOrderNotifyStream.ts:83`).

### 10. LOW: `PendingFillRegistry.wait` overwrites an existing waiter for the same key

- Evidence: `pending.set(key, ...)` at `PendingFillRegistry.ts:46`. The first waiter's timer later runs `pending.delete(key)` (line 40), which removes the second waiter's entry.
- Failure scenario: two concurrent `waitForFill` calls on one order id (for example a re-check overlapping a square-off wait) leave one waiter never resolved by the push and the other deleted by a stale timer. Both then time out and fall back to REST.
- Low, because the callers are serialised in practice. Not exercised in the code I read.

### 11. LOW: `buyChunked` continues after a chunk fills short

- Evidence:
  - `buyChunked` simply adds `trade.quantity` and loops (`chunkedOrder.ts:100-103`). `manualBuyChunked` stops on a short chunk (`chunkedOrder.ts:262-267`).
  - ANT's `enterPosition` returns a normal Trade with `quantity < chunk` when `resolveUnconfirmedAntBuy` finds a partial (`antExecutor.ts:309-319`).
- Failure scenario: chunk 3 of 8 fills part and its remainder is cancelled. Chunks 4-8 are still placed, and the caller gets `quantity < requested` with no error or flag.

### 12. LOW: an ANT fill resolved from the trade book can carry price 0

- Evidence:
  - `getFilledFromTradeBook` returns `avgPrice: 0` when rows have a quantity but no usable `tradedPrice` (`ANT.ts:959-960`).
  - `resolveUnconfirmedAntBuy` returns it (`antExecutor.ts:139`). `enterPosition` has a zero-price guard only for `marketEntry` (`antExecutor.ts:390`).
  - For a bracket/cover/plain entry it records `trade.price = 0` and `stopLossPrice = roundToTick(0 - sl)`, a negative number (`antExecutor.ts:337`).
- Related, unverified: `getFilledFromTradeBook` sums `filledQuantity` across rows as per-execution quantities (`ANT.ts:955-958`). `tradeBook.ts` establishes only that `tradedPrice` is cumulative. No fixture or test covers multi-row quantity semantics, so I cannot confirm quantity is not cumulative as well.

### 13. LOW: `buyToClosePosition` has no unconfirmed-fill resolution

- Evidence: on push and REST failure it rethrows with the order possibly resting (`antExecutor.ts:483-486`), whereas `enterShortPosition` resolves via the trade book and cancel (`antExecutor.ts:436-444`). It also books the requested quantity (line 493), ignoring a partial.
- Scope: ButterflyStrategy path only.

### 14. LOW: no non-positive-price guard on the Kite path, and quote failures are untagged

- Evidence:
  - The central price returns 0 when a side is empty (`orderPriceCore.ts:20-21` over `getLiveQuote` zeros, `ANT.ts:534-536`; `orderPrice.ts` has no guard by design).
  - ANT refuses it (`orderTypeFor`, `ANT.ts:47-52`). `Kite.placeLimitBuyOption`, `placeLimitSellOption` and `placeShortEntryOption` forward any number.
  - Also, `getOrderPrice` or `getLiveQuote` throwing means nothing was sent, but the error is not tagged NOT_PLACED.
- I could not verify how the Kite server answers a LIMIT order with price 0.

### 15. LOW/MEDIUM (security): credentials in source

- ANT `appKey` and `apiSecret` (`ANT.ts:58-59`), Kite `apiKey` and `apiSecret` (`Kite.ts:35-36`) are literals in tracked files. CLAUDE.md puts configuration in `.env`; these are not there. Rotate if the repo is ever shared.

### 16. LOW (feature.md accuracy)

- "ANT: market-with-protection buy, marketable-limit fallback": every ANT `placeOrder` call passes a price (limit at best bid or fixed). `marketProtectionPercent` is accepted and validated by `enterPosition` (`antExecutor.ts:203`, `antExecutor.ts:253-257`) but never used, and `ANT.placeOrder` sends it only when `price` is undefined (`ANT.ts:716`). There is no market-with-protection path in effect.
- "Margin rejection handling (reduced-quantity retry)": the reduced-quantity retry exists only in `strategy/BulkPcrStrategy.ts:1938-1955` (BulkPcr slot logic). The executors and `chunkedOrder` have none. `exitRejectPolicy.ts` only classifies a margin reject so it is not re-placed.
- "Central order pricing for all market/LTP-intent orders": accurate for entries. Stop/EOD/exit sells price themselves (ANT ltp x 0.99 at `antExecutor.ts:1144`; Kite min(ltp, bid) x 0.95 at `kiteExecutor.ts:102-113`), as `orderPrice.ts` states.
- `knownLtp`/`entryLtp`/`sizingQuote` in `antExecutor.ts` are dead (the `knownLtp` parameter is never read), so the comment that the sizing price becomes the entry price is stale.

### 17. LOW: Kite instrument master is downloaded daily by code

- `KiteContractMaster.ts:56-81` (runtime) and `:85-99` (startup) fetch from `api.kite.trade` whenever the file mtime is not today, which the git status of `data/kite/*.csv` is consistent with. A user memory note (contract_masters_monthly) says masters refresh monthly only. I did not read that note beyond its index line, so I cannot say whether this conflicts; worth confirming intent. Startup does a blocking `execFileSync` of up to 25 s per exchange.

### 18. LOW (latent): freeze-quantity table treats other indices as NIFTY

- `isIndexTsym` lists BANKNIFTY, FINNIFTY, MIDCPNIFTY and BANKEX (`util/underlyings.ts:9-13`). `defaultFreezeQty` gives any such NFO symbol 1755 (`chunkedOrder.ts:80-83`), and `exchangeForTsym` calls BANKEX NFO (`underlyings.ts:20-21`). The other indices have their own freeze limits. Latent only: `STRIKE_STEP` knows only NIFTY and SENSEX, so no such order can be built today.
