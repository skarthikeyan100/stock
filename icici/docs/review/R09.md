## Findings

### 1. HIGH: Hourly can never enter: the pending confirmation is always one bucket too old when it is checked

- `HourlyStrategy.ts:352` fires the entry only when `pendingConfirmation.confirmedAtBucket + TEN_MIN_MS === bucket`.
- The confirmation is created at `:358-367` on the first tick of bucket B (the closed candle is bucket B-10min), with `confirmedAtBucket = closed.bucket = B - 10min`. The entry check at `:352` runs only on a later candle change, whose bucket is at least B + 10min. So `confirmedAtBucket + 10min` equals B and can never equal B + 10min or later. `:355` then drops it as "stale".
- Reproduced by simulation (scratchpad, not committed): resistance 100, candle A at 10:00 with body 105-106, first tick of 10:10 creates `pending {"direction":"call","slLevel":105,"confirmedAtBucket":...}`; ticks through the 10:20 candle open produce `entries []`. The spec comment ("entry on the OPEN of the very next 10-minute candle after the confirming close", `:31-33`) would need the entry to run on the same tick that creates the confirmation, or the comparison to be `=== bucket - TEN_MIN_MS`.
- Scenario: strategy is enabled, a valid breakout is confirmed, nothing is ever bought, on any broker. History: the condition is unchanged since the strategy was added (`git log -S` shows only commit d68701b). The strategy is `enabled: false`, so there is no live exposure, but feature.md's "entry next candle open" is not delivered by this code. The whole exit/invalidation/reconcile machinery below it is therefore untested in production.
- Fix direction: set the entry check against `this.pendingConfirmation.confirmedAtBucket + 2 * TEN_MIN_MS === bucket`, or perform the entry immediately on the tick that opens the candle after the confirming one.

### 2. HIGH (feature non-functional when enabled; disabled today): `srHypothesis` block is absent from `config.yml`

- `SupportResistanceStrategy.srConfig()` reads `(configService.getConfig() as any).srHypothesis` and dereferences `sr.confirmWindowMin` etc. with no default (`SupportResistanceStrategy.ts:69-77`); the breach handler dereferences `sr.heldMinSec` (`:155-157`).
- `grep srHypothesis config.yml` returns nothing, and `git show HEAD:./config.yml` has no such block either. `src/prism/configValidation.ts` does not mention it, so nothing rejects the config. feature.md line 107 and `strategies.md:443` both say the block exists.
- Scenario: set `SupportResistanceStrategy.enabled: true`. Every NIFTY tick throws `TypeError: Cannot read properties of undefined (reading 'confirmWindowMin')` inside `processNiftyQuote` (after the EOD close and gates, `:151`). The strategy never trades; the dispatcher's `isolate()` swallows the error, so it shows only as log noise. The tests inject the block themselves (`src/test/supportResistanceStrategy.test.ts:113-141`), which is why they do not catch it. `open-review-items.md` item 79 reports this test failing for an unrelated-looking reason and still open.
- Fix direction: restore the block in `config.yml` (values the test uses: confirmWindowMin 3, maxJump 15, maxRangeWidth 25, buffer 8, breachBuffer 5, breachConfirmSec 15, heldMinSec 407, heldMaxSec 651), and add validation that fails closed when SupportResistanceStrategy is enabled without it. Per CLAUDE.md I did not touch `config.yml`.

### 3. MEDIUM: a failed hedge for a CLOSED leg is never retried (SimpleContinuous and ScaledHedged): the chain ends and the day goes idle

- Retry of a held-back hedge runs only for legs with `hedgeWaiting` (`SimpleContinuousStrategy.ts:652-658`, `ScaledHedgedStrategy.ts:744-750`). Closed legs receive no option ticks (`unwatch`), so Nifty-tick retry is their only path.
- Every failure path of `hedge()` that resets `hedged = false` leaves `hedgeWaiting` false: contract lookup failed (`Simple:728-732`, `Scaled:889-893`), buy definitely not placed (`Simple:696-700`, `Scaled:855-860`), cancelled with 0 filled (`Simple:705-710`, `Scaled:864-869`). The log line says "will retry" but nothing retries it for a closed leg. The `hedgeWaiting = false` at `Simple:682` / `Scaled:825` also clears a pending wait just before the buy attempt.
- A second route to the same state: `hedge()` returns silently when `this.busy.has(leg.id)` (`Simple:670`, `Scaled:782`). The sell-fill event (`updateTrade`, `Simple:778`, `Scaled:939`) can arrive while the same leg's busy slot is held by a tick-driven `placeSell`/`placeShortfall` (chunked placement takes seconds), so the hedge call is dropped with `hedged` still false.
- Scenario: a hedge leg's resting sell fills at +priceDiff; the follow-up same-direction hedge buy is refused (`[NOT_PLACED]`, margin, or ANT queue timeout) once. The closed leg is un-hedged forever, no open leg remains, and the root gate stays shut (`Simple:399`: a root exists, not `restarted`), so the strategy takes no further order that day while the trader assumes a chain is running. For an open leg the adverse-tick path (`Simple:617`) does retry, so the exposure is on closed legs only.
- Fix direction: when `hedge()` fails or is skipped for a closed leg, set `hedgeWaiting = true` and `hedgeSame = same` (as the stacking-guard branch already does) so `retryWaitingHedges` picks it up.

### 4. MEDIUM: SupportResistanceStrategy has no unconfirmed-buy latch, so an unresolved root buy can be bought twice (and ContinuousStrategy depends on tagging that R03 shows is incomplete)

- `SupportResistanceStrategy` builds its LegManager without `onSpawnBuyError` or `isOrderingBlocked` (`SupportResistanceStrategy.ts:49-58`), unlike ContinuousStrategy (`ContinuousStrategy.ts:68-69`). `tryOpen` catches a root-buy error, logs it, and records the trigger time only on success (`:174-181`), so the 60 s cooldown does not apply after a failure.
- Scenario: a root buy ends in an unresolved fill (tagged `[ORDER_MAY_BE_LIVE]`/`[HEDGE_UNCONFIRMED]`) or an untagged ANT/Kite timeout (R03 findings 2 and 3 mean the timeout is untagged). No leg is registered, so `hasOpenLegOfRight` is false (`:170`) and the next confirmed breach on that side buys again: two live buys, one tracked.
- ContinuousStrategy handles the tagged case (`noteUnconfirmedBuy`, `:75-79`, `:309`) but an ANT `ambiguousPlacement` / Kite timeout error is not tagged, so `isUnconfirmedBuyError` is false, `ordered` is reset (`:310`) and the next tick after the cooldown buys again. Same root cause as R03 #2; fix it there.
- Fix direction: give SupportResistanceStrategy the same `manualReview` flag, `onSpawnBuyError` and `isOrderingBlocked` hooks, and call `noteUnconfirmedBuy` in the `tryOpen` catch.

### 5. MEDIUM: Simple/Scaled root buy of unknown outcome is held only in memory; a restart re-opens a second root

- On an unresolved root buy (`res.kind === 'unknown'`) the strategies set `this.manualReview = true` (`Simple:446-449`, `Scaled:531-535`) and record nothing durable. ScaledHedged persists `pendingHedge` for hedge buys (`Scaled:873`) but has no equivalent for the root. `manualReview` is a plain field (`Simple:116`) cleared on every process restart (CLAUDE.md notes restarts are frequent and "No In-Memory-Only Controls").
- Scenario: the root buy times out, the broker cancel or position read fails (`unknown`), the strategy latches. A hot restart follows. The state file has no root leg, `manualReview` is false, reconcile has nothing to adopt if the order is still resting un-filled, so the root gate (`Simple:399`) is open and a new root is bought while the first may fill later.
- Fix direction: persist a pending-root record in the state file (as `pendingHedge` does) and keep the root gate shut and the buy blocked until it is settled.

### 6. MEDIUM/LOW: a failing PCR fetch is retried on every NIFTY tick in Simple and Scaled (no throttle)

- `direction()` leaves `lastPcr = null` on failure (`Simple:369-371`, `Scaled:433-435`) and caches only on success, so the 5-minute re-check gate (`:363`/`:427`) is not reached again until a success. `ANT.getOptionChainPCR` makes two POSTs per call and throws on any failure (`ANT.ts:611-627`, `orderProcess.ts:1371-1373`). `entering` prevents overlap but not a call per tick, once per second or faster while the root gate is open.
- Scenario: ANT session expired or option chain rate-limited: each tick issues two REST calls via the order process and logs a failure. ContinuousStrategy deliberately throttles (`:189-193`, `lastPcrCheckTime` set before the call).
- Related fact: PCR comes only from the ANT option chain, so a kite/breeze/prism instance cannot enter without a valid ANT session (fails closed, no order risk).
- Fix direction: set a `nextPcrTry` time on failure.

### 7. LOW: non-finite or tied PCR silently picks CALL

- `pcr > 1 ? PUT : CALL` (`Continuous:219`, `Simple:374`, `Scaled:438`). A NaN PCR (a non-numeric `oi` makes `Number()` NaN; `ceOi === 0` is not true for NaN, `ANT.ts:621`) and PCR exactly 1 both return CALL. No `Number.isFinite` check.
- 7b (Scaled): `hedgeQuantity` returns `Math.max(q, base)` (`Scaled:777`), so a non-lot-multiple `initialQuantity` gives a non-lot hedge quantity while the root is floored to whole lots (`:509`). Config has 260 (4 lots), so no live effect. A NaN `priceDiff` also yields a NaN hedge quantity; the root gate (`:463`) prevents it only while config stays valid.

### 8. LOW: SupportResistanceStrategy has no entry time window

- `processNiftyQuote` has no `isTimeInRange()` call and the class does not override it (`SupportResistanceStrategy.ts:133-165`); ContinuousStrategy limits entries to 09:30-15:00 (`Continuous:85-91`). Entries are possible from 09:15 to `eodCloseTime` (15:10); a root bought at 15:09 is closed by the EOD sweep a minute later. Not a feature.md claim.

### 9. LOW: Hourly - the last 10-minute candle of every clock hour can never confirm a breakout

- `processNiftyQuote` calls `rollHourIfNeeded` before `updateTenMinCandle` (`HourlyStrategy.ts:200-204`). On the first tick of a new hour, `resistance`/`support` are replaced by the hour just finished (`:262-263`), and then the candle that ended at that same instant (the hour's last candle) is tested against them (`:358-361`). That hour's high includes the candle's own highs, so `bodyLow > resistance` / `bodyHigh < support` is impossible. Also `rollHourIfNeeded` nulls `pendingConfirmation` (`:269`) before the entry check. (Derived from code order, not run; moot while finding 1 stands.)

### 10. LOW: ScaledHedgedStrategy header comment contradicts the code

- `ScaledHedgedStrategy.ts:41-74` still describes item 1 (`onePositionPerSide` sizes the root), item 5 (double-up of the parent), item 6 (`maxInvestment` gates only the root, hedge and double-up ignore it) and item 9, while code and the lettered A-G rules above them say the opposite (`onePerSide()` always true `:716`, root = `initialQuantity` `:509`, no add `:793`, cap on every buy `:840`). `onePositionPerSide: true` in the config block has no effect on this class. A reader following the header would mis-size a trade.

### 11. LOW: `maxLegsPerSide` counts only registered legs, not in-flight hedge buys (SimpleContinuous, `onePositionPerSide` off)

- `sideBlocked` filters `openLegs()` (`Simple:639-640`); `pendingSides` is used only in `onePerSide` mode (`:684`). Two different legs hedging the same side in the same moment can both pass and exceed the cap by one. Config currently has `onePositionPerSide: true`, so inactive.

### 12. LOW: Hourly can buy into an already-invalidated position

- Entry happens at the next candle's open without comparing it with `slLevel` (`HourlyStrategy.ts:374-413`). If the open gaps through the confirming candle's low (CALL) or high (PUT), `checkInvalidation` fires as soon as the exit sell is placed (`:278-293`), giving a certain round trip. Also the comment at `:175-176` says the first level is available at 10:15; code actually has it at 10:00 (rollover of the 09:15-10:00 hour), candle tracking merely starts at 10:15.

### 13. INFO: how R03's ANT/Kite ambiguous-placement finding applies to this chunk

- SimpleContinuous and ScaledHedged are NOT exposed on buys: `noteBuyError` treats only a positive `[NOT_PLACED]` tag as safe and every other error (timeout, transport, untagged) as may-be-live, resolved against the broker (`Simple:264-273`, `Scaled:309-318`). Their sells retry on a timer, but the never-short guard bounds oversell.
- ContinuousStrategy and SupportResistanceStrategy (LegManager) ARE exposed: only `[HEDGE_UNCONFIRMED]`/`[ORDER_MAY_BE_LIVE]` count (`LegManager.ts:154-157`; free-the-slot path `:1346`, `:1402`); see finding 4.

### 14. LOW (unverified trigger): fill events are not de-duplicated in Simple/Scaled `updateTrade`

- `noteSeenSells` only appends the order id (`Simple:748`); `updateTrade` never checks it before `soldQty += qty` (`:754`). A re-delivered Sell event (not shown to occur in code I read; dedup, if any, lives in the order process, R07/R03) would close the leg early and trigger a hedge while the position is still held. Reported for the owner of the event path to confirm.

## Items checked, no defect found

- Simple/Scaled `hedged = true` is set synchronously before the first await in `hedge()` (`:683`/`:826`), and `pendingSides` makes the side check atomic; no double hedge found.
- Reconcile for all five paths restores state without placing orders (relies on `withNoOrders`); a disabled strategy's `reconcile()` only updates state (`Scaled.cancelStrandedSells` is gated by `enabled` at `:444`).
- Per-broker `maxInvestment`: the `maxInvestmentByBroker` in the Simple block is honoured via the per-instance expansion, not by the strategy code; verified in `strategyInstances.ts:28`.
- NaN handling in the max-profit total is delegated to `finiteGuard.ts` (`Simple:161-171`); `priceDiff`/`maxProfit` gates reject non-positive/NaN before a root (`Simple:396`, `Scaled:463`).
