## Findings

### 1. Broker API secrets are hard-coded in tracked source and have been in git history since the first commit - high
- Code: Kite `apiKey`/`apiSecret` (src/kite/Kite.ts:35-36), Breeze `appKey`/`appSecret` (src/breeze/Breeze.ts:74-75), ANT `appKey`/`apiSecret` (src/ant/ANT.ts:58-59), and a second ICICI `api_key` inside a dead `loginUrl` (src/prism.ts:52). All four files are tracked (`git ls-files`), the secrets appear in history (`git log -S`: dd9219f "Integrated with ant, kite and prism" for Kite and ANT; b3f4d78 for Breeze) and `origin/main` exists (git@github.com:skarthikeyan100/stock.git).
- Scenario: anyone with read access to the repo or its remote (or a leaked clone/backup) can compute the ANT checksum (`sha256(userId + authCode + apiSecret)`, ANT.ts:209) and call Kite `generateSession(request_token, api_secret)` / Breeze `apiUtil` themselves. Combined with finding 2 that is an account-takeover primitive for the platform's broker sessions; alone it lets a third party mint sessions on the platform's registered apps once they obtain any user's login redirect. Prism already reads its credentials from env (RestAPI.ts:48-54, .env.example:76-85), so the pattern exists; the other three do not follow it.
- Remedy (for the owner to decide): rotate all three secrets at the brokers, move them to `.env` (fail-closed like SESSION_COOKIE_SECRET), and consider history rewrite for the remote.

### 2. Broker login/callback routes are unauthenticated and carry no OAuth `state`: anyone can replace the platform's broker session - high
- Code: `router.get('/<broker>/login')`, `router.get('/<broker>/callback')`, `router.post('/breeze/callback')`, `router.get('/shoonya/callback')` (src/routes/brokers.ts:112-120) have no `requireAdmin`/`requireAuth`, no CSRF header (the global guard explicitly exempts `/breeze/callback`, server.ts:101-104, and is GET-exempt for the rest) and no `state`/nonce binding the callback to the browser that started the login. The Cloudflare worker forwards `/ant`, `/kite`, `/breeze`, `/shoonya`, `/prism` to the origin (cloudflare/_worker.js:5), so they are reachable from the internet, not only loopback.
- Scenario (login CSRF / session fixation): the platform's Kite `api_key` is public by design (GET /kite/login redirects to it). An attacker opens that login URL, signs in to his OWN Kite account, and receives a `request_token` valid for the platform's app. He sends `GET https://nivedhatech.com/kite/callback?request_token=<his token>`. `exchangeToken` (brokerClients.ts:48-52) runs `generateSession(requestToken, apiSecret)` with the platform's secret, `saveSession()` writes `.kite_session.json`, and `reloadSession` pushes it into the order process (brokers.ts:86-94). The platform now trades through the attacker's account; the real session is lost; reconcile reads the attacker's positions. The same works for ANT (`authCode` + `userId` query, brokers.ts:43), Breeze (`apisession` as GET query or POST form, brokers.ts:54, no CSRF header needed) and Shoonya (`code`).
- Mitigation sketch: require an admin session cookie (or loopback) on the callbacks and issue/verify a random `state` per login attempt (Breeze's POST redirect cannot carry the Lax cookie, so a server-side one-time state that `/breeze/login` creates is the practical binding there).

### 3. Prism: a partial fill is never booked on a cancelled/timed-out order (live lots unknown to bookkeeping) - medium
- Code: `Prism.getOrderStatus` returns `fillPrice` ONLY for status COMPLETE (src/prism.ts:707-709); the CANCELLED/REJECTED branches return `{status, filledQuantity}` with no price (:719-725). `waitForPrismBuyFill` then (a) tests `Number(filledQuantity) > 0 && fillPrice` before reporting a partial (prismExecutor.ts:141) - never true; the order falls through to a plain refusal that is NOT flagged `partial` and, for CANCELLED with fillshares > 0, not flagged not-placed either (:150); (b) after the timeout cancel, the re-check returns `{outcome:'partial', avgPrice: Number(finalCheck.fillPrice ?? 0)}` = 0 (:171), so the thrown error carries `averagePrice: 0`. The two booking sites require `e.averagePrice > 0` (prismExecutor.ts:96 sellContract, :240 buyOnPrism), so neither books.
- Scenario: a Prism limit buy fills 650 of 1300, rests until the 12.5 s poll ends, is cancelled. The error reaches the strategy as "did not fill", 650 lots are live at Shoonya, no Trade row, no exit monitor, no stop. The same on a partial sell leaves the booked position larger than the broker's. (The pending-order poller path is fine: `rowPrice` reads `avgprc` from the order-book row, pendingPrismLimitOrders.ts:55-58.) Fix is to return `avgprc` for partial/cancelled records in `getOrderStatus`.

### 4. Breeze order-notify socket is never re-authenticated after a re-login and never re-subscribed after a drop - low/medium
- Code: `BreezeOrderNotifyStream.connect()` returns at once when `connected` is true (:80-83) and `connected` is only reset by a manual `disconnect()` (:186-189). The SDK creates the order socket once, capturing `auth: {token: sessionKey}` at creation (breezeConnect.js:80-88) and only when `self.socketOrder` is null (:211-216). `Breeze.generateSession` swaps `sessionKey` (Breeze.ts:359) but nothing recreates the order socket, and `onSocketConnect/Disconnect/Error` hooks attach to `breeze.socket` only (Breeze.ts:262-282), never `socketOrder`.
- Scenario: Breeze token dies mid-session, the trader logs in again (`reloadSession` -> `connectBreezeOrderNotifyIfSessionValid`, orderProcess.ts:1241) - the stream reports "Already connected" and keeps the dead socket. Every later Breeze fill waits the full push budget (fillWaitPlan: 45% of 54 s = 24.3 s) before the REST fallback confirms it (breezeExecutor.ts:55-65), delaying every Breeze buy/exit by ~24 s. A silent socket drop behaves the same. Correctness is preserved by the fallback; latency and the 90 s IPC budget are the cost.

### 5. Breeze trade-book reads cover NFO only: SENSEX (BFO) Breeze fills are invisible to attribution and debug reads - medium
- Code: `getTradeList({exchangeCode: 'NFO'})` at brokerClients.ts:68, bookkeeping.ts:2121 and bookkeeping.ts:2470. The master and executor fully support BFO (BreezeContractMaster.ts:98-100, `probeOrderExchange` tries NFO then BFO, breezeExecutor.ts:112-121), and config.yml:226 gives BulkPcr-SENSEX a Breeze allotment.
- Scenario: a non-platform sell (or a platform fill needing trade-book resolution) of a SENSEX option on Breeze is never in the timed-fills / non-platform-sell reads, so the "book foreign sells at the trade-book price" path (bookkeeping.ts:2121 and :2470) sees nothing for BFO: the lots stay booked as held, or are attributed with the logged fallback. `/broker/breeze/trades` likewise never lists SENSEX.

### 6. `check-broker-sessions.sh` reports Breeze as invalid on any day Breeze traded nothing - low
- Code: the script probes `GET /broker/breeze/trades` (check-broker-sessions.sh:130) which calls `getTradeList`; Breeze answers an empty list with Error "No Data Found" (confirmed by bookkeeping.ts:2123-2124 comment: "live every sync on a day Breeze traded nothing"), `callSdk` throws (Breeze.ts:127-129), the route answers 500 "Failed to fetch trades", the script prints `FAIL`. A valid session therefore reads as FAIL before the first Breeze trade of the day and the summary exits non-zero. Probe `positions` (already special-cased for "No Positions available", Breeze.ts:519-521) or `hasValidSession` instead.
- Also the probe runs in the `frontend` process's singletons (BROKER_CLIENTS), not the trading process that places orders, so it can disagree with `brokerSessions` (which asks the order process).

### 7. Breeze/Shoonya definite rejections are not tagged `[NOT_PLACED]`; error diagnostics race on a module global - low (overlaps R03)
- `Breeze.callSdk` turns an ICICI error envelope (a definite refusal such as "Available Futures and Options Limit is insufficient") into a plain `Error` (Breeze.ts:127-129); neither Breeze.ts nor breezeExecutor.ts contains `markNotPlaced`/`notPlaced` (grep: no matches), while Prism does mark its answered rejections (prism.ts:1232-1237). orderProcess.ts:1390 only emits `[NOT_PLACED]` for tagged errors, so a Breeze margin rejection reaches the strategy as an unknown outcome instead of a safe-to-retry refusal. R03 owns the executor policy; recorded here because the tag belongs at `callSdk`.
- `lastBreezeHttpError` is a module global reset at the start of every `callSdk` (Breeze.ts:37, 118): a quote poll starting while an order call is in flight clears the order call's captured ICICI error body (the SDK's own re-throw discards it, Breeze.ts:18-26), so the real rejection text (which `maxProfitLock.ts:92` and `exitRejectPolicy.ts:14` pattern-match for margin/non-transient errors) degrades to "breezeconnect SDK threw with no recoverable diagnostic". The code comment concedes it is "NOT concurrency-safe".

### 8. Prism contract master: claims in feature.md are overstated and its cache never refreshes - low
- feature.md line 3 lists exact-expiry lookup, strike-by-premium and lot size for all four masters. `PrismContractMaster` has only `findNearestExpiryOption` (offset-based), `findATMOption` and `upcomingExpiries` (PrismContractMaster.ts:65-117): no exact-expiry lookup (the Prism path re-resolves by strike to "nearest", so a sell can hit a different expiry than the buy when the nearest/skip rule flips), no lot size (taken from ANT's record, prismExecutor.ts:459; `Prism.findLotSizeByContract` does read column 2 but returns a string and is used only by the legacy buy path), no BFO (the file read is NFO_symbols.txt only; `assertPrismExchange` refuses BFO, prismExecutor.ts:334-336 - fine, but SENSEX on Prism is unsupported and feature.md does not say so).
- No refresh: unlike Kite (daily, KiteContractMaster.ts:56-108), Breeze (daily, :217-235) and ANT (hot-reload on mtime, :82-117), `cache` in PrismContractMaster (:26, :43) and `Prism.lines` (prism.ts:361-381) are loaded once per process and never invalidated. After `scripts/download-all-masters.sh` the running trading process keeps the old Prism rows until restart (the script's own footer, lines 118-124, says so but is also stale for ANT/Kite/Breeze, which do reload); `verifyMasterFiles` alerts only at 30 days (masterFiles.ts:25).
- Scenario: Prism NFO file is 3 weeks old (no ALERT yet), the nearest listed expiry in the file has passed, `findNearestExpiryOption` returns the next one (or throws) and a strike for a newly listed weekly is "not found". Low because Prism is a secondary broker.

### 9. Breeze tsym falls back to the expiry-less form and the legacy form matches every expiry - low
- `breezeTsym` silently emits the old `NIFTY24950CE` when the expiry text cannot be read (BreezeContractMaster.ts:78-81) - the exact collision that caused the 2026-11-09 double buy; it logs nothing. Live file formats are `DD-Mmm-YYYY` (checked), so it is latent, but a master format change would silently re-open the bug.
- `positionMatchesTsym` (breezeExecutor.ts:141-143) matches a legacy tsym against ANY expiry's position of that strike; `getLiveNetQuantity` (:923) and the sell path (:397) take the first match, so a legacy-spelled leg with two expiries held returns one expiry's quantity. Only reachable from state written before 2026-11-09.
- `parseBreezeTsym` accepts letters only in the underlying (BreezeContractMaster.ts:90): a stock underlying such as `M&M`/`BAJAJ-AUTO` does not parse. Breeze is used for indices only today.

### 10. ANT master: default strike step 50 for any unlisted underlying; before 05:30 IST the "today" cut-off is yesterday - low
- `AntContractMaster.STRIKE_STEP[symbol] ?? 50` (AntContractMaster.ts:190, :201) silently rounds BANKNIFTY/FINNIFTY/stock indices to 50 while PrismContractMaster knows BANKNIFTY=100 (PrismContractMaster.ts:106); `pickContractByPremium` (priceRangeContract.ts:17) is two-valued. Only NIFTY/SENSEX are traded now, so latent.
- `todayStartUtc()` is the UTC day start (AntContractMaster.ts:15-17); between 00:00 and 05:30 IST it is yesterday's midnight, so an already-expired contract still counts as "nearest" in that window (harmless while the market is closed, wrong for any pre-05:30 job).

### 11. Login helper leaves a Chrome profile with broker session cookies on disk on failure/dry-run - low
- scripts/login.js:261 creates `mkdtemp(os.tmpdir()/icici-login-*)` and removes it only on full success (:301-303). On any failure or `--dry-run` it `browser.disconnect()`s and leaves Chrome running with that profile (:296-299), and the failure report writes a screenshot of the broker page to `/tmp/icici-login-<broker>-fail.png` (:243-245). Profiles hold the broker sites' cookies/tokens (and, in a dry run, the typed user id/password may sit in autofill state); /tmp is world-listable by default. Worth a `chmod 700` of the profile dir and cleanup on exit. (broker-credentials.json itself is mode 600, git-ignored, and the script warns on loose modes, :51.)

### 12. Broker-name migration script is partial - low (latent)
- migrate-broker-names.js rewrites `Trade`, `closedTrades`, `strategyLatches` and three strategy-state collections only (:571-592). Collections that also store `broker` (orderOwners, lockedSells, mirrorLegs, legLineage, pendingKite/Ant/Breeze/Prism limit-order collections) are not touched, and reads in those paths do not apply the `zerodha` alias (the alias-tolerant filters exist only in bookkeeping.ts:1842, :1870, :1905, :2499, :2678, :2826). Read-only check today: 0 legacy `zerodha|aliceblue|shoonya|icici` rows in 14 such collections, so nothing is broken now. The script also hard-codes `mongodb://localhost:27017/stocks` (:569) instead of the app's configured URL.

### 13. Raw Breeze order-notification payloads (client code and account number) are logged on every push - low
- BreezeOrderNotifyStream.ts:108 logs `JSON.stringify(data)` for every push, and the push carries `userId` (ICICI client code) and `orderMatchAccount` (account number) (orchestrator.log 12:25:42: `"userId":"SSUKK001"`, `"orderMatchAccount":"8502440688"`). These land in orchestrator.log, which the monitor/skill scripts print and which can be pasted into reports. The comment justifying it (diagnosing `averageExecutedRate`) is stale now that the fill price is known to come from `cancelFlag` (:135-142). Consider logging only the fields used.
- ANT/Kite exchange also log the first 20 characters of the auth code / request token (ANT.ts:200-201, Kite.ts:143) and a 20-character prefix of the ANT checksum (ANT.ts:214): single-use values, but a prefix of a SHA-256 over the API secret is unnecessary.

### 14. Paper broker: fills booked-failed still count as filled; market exits use an unbounded-age tick - low
- `fillOrder` records the fill in `fills` (via `fillTrade`, paperExecutor.ts:82) and `filledQty` before `bookkeeping.recordFill`; if that throws it only logs an ALERT (:105-109). `marketBuyOf` finds the `fills` row and returns the Trade as "already booked by the fill itself" (:233-238), so the strategy believes the leg is held while bookkeeping has none (and `paperBook` shows it). In-memory broker, so impact is confined to paper P&L correctness.
- `marketPrice` (:137-143) uses the last tick of any age for exits, unlike `marketForBuy`, which requires a tick under 5 s old (:160-168). If the token's subscription was released (`releaseTick` when the last order for it is gone, :74-79) and nothing else subscribes it, a paper stop/EOD exit fills at an arbitrarily old price.
- Note on `crossCheckQuote` (quoteCrossCheck.ts:3-8): with an empty bid list (`q.bestBid` 0 and no live bid) `Math.min()` is Infinity and the returned `bestBid` is Infinity; with no ask source `Math.max()` is -Infinity. Unreachable today (see checklist) but it will mis-price if a new caller passes an unvalidated quote.
