## Findings

### 1. MEDIUM: any intraday sync or reconcile marks the day as "EOD done", so the after-close sync never runs

- Evidence: `runEodRepair` writes `eodReconcileRuns/<today>` with `ok: r.ok` per broker whatever the context or time (`orderProcess.ts:1584-1590`). `eodReconcileTick` runs only the brokers whose marker is not `ok === true` (`:1614-1616`) and returns when none are pending. `POST /reconcile`, `POST /sync` and `npm run sync` all call `runEodRepair` through `runEodRepairNow` (`:1298-1318,1600-1603`). `ok` is also true for a broker that "is not readable and has nothing open" (`bookkeeping.ts:2767`).
- Failure scenario: the operator logs in and calls `POST /reconcile` at 09:30 (the documented step after a login) or runs `npm run sync` at noon. All four brokers report ok and the marker is stored. At 15:45 the scheduled run sees nothing pending and does nothing. The ANT 15:16 MIS square-off, GTT fills and manual sells made after the manual run are not repaired into Mongo that evening. The next morning's restart restores from Mongo alone, so the position comes back as open (the exact failure `syncExternalCloses` was written for, 2026-11-11).
- Fix direction: store the marker only for runs made at or after `effectiveEodReconcileTime()`, or store the run time and require `at >= eodReconcileTime`.

### 2. MEDIUM: expiry-day force close keys off NIFTY only; SENSEX positions are not swept on SENSEX expiry day

- Evidence: `isNiftyExpiryDay` asks the master for `nearestExpiryDayMs('NIFTY')` only (`marketHours.ts:35-43`). The sweep runs only when it returns true (`:44-49`, `orderProcess.ts:1782`). Master check: NIFTY expiries in `data/ant/NFO_contract.json` are 2026-11-23 (Mon), 2026-12-01, 2026-12-08 (Tue); SENSEX CE expiries in `data/ant/BFO_contract.json` are 2026-11-26, 12-03, 12-10 (all Thursday).
- Failure scenario: BulkPcr-SENSEX or any SENSEX leg is still open on Thursday 2026-11-26 at 15:15. Nothing here sells it, although feature.md line 82 says "every open position" and the header comment says expiry-day positions must be closed by 15:15. Whether a strategy's own EOD close (`settings.eodCloseTime`) covers it was not checked in this chunk. The reverse also happens: on a NIFTY expiry day the sweep sells SENSEX positions that do not expire.
- Fix direction: sweep a trade when its own contract expires today (the token's `expiryMs` from the master), not on the NIFTY calendar.

### 3. MEDIUM: a chunked square-off that hits an unconfirmed (PENDING) chunk stops silently, and the callers treat it as done

- Evidence: `squareOffChunked` does `break` when a chunk returns `status === 'PENDING'` and then returns the quantity confirmed so far without throwing (`chunkedOrder.ts`, in `squareOffChunked`, "placed but fill unconfirmed ... stopping"). ANT returns PENDING from `squareOffOnAnt` when the fill is not confirmed (`antExecutor.ts:1196-1205`). `squareOffAutoChunked` wraps that result as a normal Sell trade. The exit monitor unregisters the watch before calling the handler and re-registers only on a throw (`exitMonitor.ts:329-344`), so a return is treated as success. `forceCloseTrade` returns true and holds its 2 min cooldown.
- Failure scenario: an ANT position above one freeze order (NIFTY above 1755 units, only reachable from a split frontend buy) hits its stop. Chunk 1 is placed but the push and the status read both fail to confirm it. The loop stops. Chunks 2..n are never sent, the exit monitor has dropped its watch, and no error is raised. The re-price chain only handles chunk 1's order. The rest of the position has no stop until a restart's `reconcileFromTrades`. For a drawdown breach or the 15:15 sweep the next attempt is only after the 2 min cooldown.
- Note: the same shape without chunking is handled on purpose (the re-price chain owns that one order); the defect is that the unsent chunks are dropped. Also not covered here: `squareOffOnKite`/`squareOffOnAnt` market-style exits still take no sell lock (R03 finding 5), so the force-close sweep, the exit monitor and a strategy can start sells for the same row at once. Kite and ANT have the `pendingSquareOffs` duplicate guard; whether Breeze and Prism have an equivalent was not checked.
- Fix direction: on PENDING, throw (or return a flag) so the caller keeps the watch and retries the remainder.

### 4. MEDIUM: `setTargetStopLoss` only changes the numbers for Kite positions without a GTT and for every ANT position

- Evidence: `setTargetStopLossOnLeg` (`kiteExecutor.ts:424-456`) writes `trade.targetPrice/stopLossPrice`, modifies a GTT only when `trade.gttTriggerId` is set, and starts an exit-monitor watch only for `trade.broker === 'breeze'`. There is no ANT modify call (grep of `antExecutor.ts` and `ANT.ts` for modify/setTarget: none). The IPC case calls this for every broker (`orderProcess.ts:1225-1229`), and so does the admin mirror (`mirror.ts:196-206`).
- Failure scenario 1: a Kite position bought without exit points (no GTT, not watched), then the user sets target/stop in the UI. The UI shows the new levels; no GTT or watch exists, so nothing exits. `attachProtection` is the function that arms them, but it is not called here.
- Failure scenario 2: an ANT bracket position (`antOrderNo`). The broker bracket keeps the original prices and the exit monitor treats it as watch-only, so the edited levels are display only.
- Fix direction: after updating the fields, call `attachProtection` for a Kite/ANT leg that has neither a GTT nor a watch, and refuse (or say so) for an ANT bracket.

### 5. MEDIUM: ANT bracket exit ignores the requested quantity and books at a guessed price

- Evidence: when the row has `antOrderNo`, `squareOffOnAnt` calls `ant.exitBracketOrder(existing.antOrderNo, orderComplexity)` with no quantity (`antExecutor.ts:1125-1131`), then books a Sell of `quantity` (the requested, possibly partial amount) at `existing.lastTradePrice ?? existing.price` (`:1214-1217`). The comment at `:1214` says no fill price is available.
- Failure scenario: a user sells half of an ANT bracket position from the UI, or the admin mirror closes a fraction of the admin's ANT leg (`mirror.ts:131`). The broker exits the whole bracket; bookkeeping records only half sold, at a last-tick price rather than the fill. The other half stays "open" in the books and the exit monitor, while the broker is flat. Realized P&L is also off by the price guess. A later exit of the remainder is refused as "nothing sellable". Only the bracket path is affected; a plain ANT order is sized and priced correctly.
- Fix direction: for a partial quantity on a bracket row, cancel the bracket and place a plain sell; or reject the partial. Read the fill from the trade book before booking.

### 6. MEDIUM: a strategy whose startup `reconcile()` throws is never retried

- Evidence: `startupReconcile` retries only when the restore or the IPC fails (`strategiesProcess.ts:185-201`). After `runReconcile()` it only logs strategies still `!stateLoaded` and returns (`:191-194`). `reconcileStrategies` logs the failure and moves on (`:165-171`). The comment at `:483-485` says it "retries until it succeeds".
- Failure scenario: a strategy's `reconcile()` throws once (for example a transient order-process error during its `openTrades` call). It keeps `stateLoaded = false`, so it receives no ticks, fills or cancellations (`receivesEvents`), and the process says "Startup restore complete" for the others. A position it holds is managed by nobody on the strategy side until someone calls `POST /reconcile`. The order-side nets (exit monitor, drawdown, expiry sweep, GTT) still run.
- Fix direction: loop `runReconcile` until every strategy is loaded (with a cap and an ALERT), as the comment says.

### 7. LOW-MEDIUM: resting entry exits are claimed before they are attached and never retried

- Evidence: `onEntryFill` deletes the `entryExits` row first (`entryExits.ts:34`), then calls `attachProtection`; on any throw it only logs an ALERT (`:37-39`). `attachProtection` throws unless `0 < stop < entry < target` where `entry` is the aggregate row's average price (`attachProtection.ts:39-43`), or when the GTT call fails and the fallback also fails.
- Failure scenario: the admin mirror of a contractor's recommendation fills while the admin already holds the same contract at a higher average, so the aggregate average makes `stop < entry < target` false. The row is gone, the ALERT is a log line, and the position has no exit. Same outcome if Mongo is briefly unavailable between the claim and the attach.
- Fix direction: delete the row only after a successful attach (or re-insert it on failure), and validate against the fill price rather than the aggregate average.

### 8. LOW-MEDIUM: lock-profits repeat after 10 min cancels the lock and re-prices lower; its sells are not in the locked-sell ledger

- Evidence: the "still open" skip is a time check only (`orderProcess.ts:690-696`, `LOCK_PROFITS_COOLDOWN_MS = 10 min`). After that, the call cancels the resting sell (`:712`) and places a new limit at the current live price rounded up (`:707`). The header comment says a repeat must not "give back locked profit" (`:575-577`). Its sells use `squareOffLimitChunked` directly and are never passed to `recordLockedSells` (`:721`), so a broker cancel or reject of a lock-profits sell is reported to the strategies instead of being re-placed at the same price (`orderProcess.ts:130-135`).
- Failure scenario: the operator calls lock-profits at 11:00 at LTP 120, the market drifts to 110, and a second call at 11:15 (for example for a newly bought leg) cancels the 120 limit on the first leg and rests it at 110.
- Fix direction: skip while the prior order id is still tracked (the tracker already knows), not by age; or record these sells as locked.

### 9. LOW: feature.md line 20 claims a startup broker session check that does not exist

- Evidence: `startOrderProcess` (`orderProcess.ts:1647-1836`) checks only master files, Mongo, limits, closed trades, the Mongo restore, trackers and ANT/Breeze notify connections (which are gated on a session but only skip with a log, `:176-195`). `startupReconcile` states the opposite: "a restart does not read any broker and needs no login" (`strategiesProcess.ts:176-179`). `brokerSessions` is an on-demand IPC verb only.
- Impact: doc claim, not a defect in behaviour; the design decision of 2026-11-11 is consistent with the code.

### 10. LOW: dead code in the order process

- `resolveRequestBroker` has `return 'ant'; return 'breeze';` (`orderProcess.ts:249-250`): the second return is unreachable and its `case` label is missing. No `breezeBuyIndex` request type exists in the protocol (grep of `src` finds the name only in comments). Harmless today because the default branch resolves the user's broker, but the comment at `:234` and `:372` still describes it.
- `startReconcile`, `reconcileAllBrokersOnce`, `runBrokerReconcileNow`, `lastReconcileResult`, `reconcileQueued` and `prismInUse` (`:1494-1556,1625-1632`) are unreferenced (`runBrokerReconcileNow` is never called; grep). The note at `:1468-1469` said to delete them after a week of clean end-of-day runs (2026-11-11). `startReconcile`'s `finally` sets `reconcileInFlight = null` unconditionally, so reviving it would clobber the Mongo-restore and EOD gates.

### 11. LOW: the poller re-entrancy guard has no timeout, and the exit monitor can drop a still-open position after 3 refusals

- Evidence: `guardedInterval` sets `running = true` and clears it only when the promise settles (`orderProcess.ts:1755-1762`). Drawdown evaluation, GTT poll and manual-sell poll have no per-call bound of their own (the trackers do: 45 s). A promise that never settles stops that poller for the rest of the process with no log.
- Also: after `NEVER_SHORT_MAX_ATTEMPTS = 3` refusals while the position is still open in the books, the exit monitor deletes the watch and logs an ALERT (`exitMonitor.ts:362-366`). If the broker holds it but the guard refused for another reason (for example "covered by other users' resting sells" is a different message, so only the real "nothing sellable" case reaches here), tracking is out of sync and the position is unwatched until the GTT poll, `POST /sync` or a restart. This is intended by the author; noted because the ALERT is log-only.

### 12. LOW: stop handling can lose writes that are not fill inserts

- Evidence: `drainOrderWrites` waits (up to 3.5 s) for `pendingFillInserts` and held closed-trade rows only (`bookkeeping.ts:3132-3139`). SIGTERM then exits at once (`tradingProcess.ts:27-30`). Fire-and-forget writes not covered: pending-order `track` (`pendingOrderTracker.ts:117-122`), `recordOrderOwner`, `recordLockedSells`, mirror rows, `persistGttTriggerId` (with its 2.5 s retry, `kiteExecutor.ts:867-885`). An order whose placement is in flight at SIGTERM is not awaited either.
- Failure scenario: a resting limit sell is placed, the process is stopped for a code change within a few ms, and the tracker row is not yet in Mongo. After the restart the order is not tracked; its fill is found only by the next sync.

### 13. LOW: admin mirror buys skip every `canPlaceOrder` gate

- Evidence: by design, `mirror.ts:10-12` ("goes straight to the broker executor, NOT through placeOrderWithPendingGuard"). So the admin leg is not subject to the global max-profit latch, the admin's daily/weekly drawdown or account closure, the lot limit, `perOrderCap` or the investment cap, and does not take a reservation. Only the user's own order is gated (and the contractor/user may be allowed while the admin is latched).
- Impact: design risk, not a bug against the stated design. After a max-profit lock or a weekly close of the admin account, a frontend or contractor buy still opens a real admin position of `floor(lots x pct / 100)` lots.

### 14. LOW: the order IPC socket has no authentication and sits in /tmp

- Evidence: `ORDER_SOCKET_PATH = /tmp/icici-order.sock` (`ipc/orderProtocol.ts:7`), created by `net.createServer().listen(path)` with no `chmod` (`orderProcess.ts:1808-1832`). Every verb, including `lockProfits`, `squareOff`, `manualBuy` for any `userId`, and `updateUserSettings` with `accountClosed:false`, is accepted from any connected client (`:1261-1264`). Socket mode follows the process umask; the project files are `rw-rw-r--`, which implies umask 002, so group members can connect. Startup also unlinks an existing path (`:1808`); in sticky /tmp a path pre-created by another user makes that fail with EPERM and stops the process. No socket file existed in /tmp when checked (processes not running).
- Impact: only relevant on a multi-user host.

### 15. LOW: order-owner and tracker records are keyed by order id alone

- `orderOwners` has a unique index on `orderId` only (`orderOwners.ts:93-104`) and `$setOnInsert` ignores `broker`. If two brokers ever issue the same id string, the second broker's order is attributed to the first writer. Paper ids are `PAPER-<ms>-<seq>` and cannot collide; real Kite/ANT/Breeze/Prism ids are different numeric/alphanumeric formats, so this is a latent rather than observed risk. Not verified against live data.

### 16. LOW: lock-profits sells every user's longs, and rows with no `broker` are skipped

- Evidence: groups are built from all of `bookkeeping.trades` with no user filter (`orderProcess.ts:671-678`), so frontend and contractor-user positions are sold under their own user id, not only strategy pseudo-users. The feature line says "all open longs", so this matches it, but the route comment and `platformSells.ts` talk about strategies. Rows with an empty `broker` are skipped (`if (!t.broker ...) continue`, `:673`), while every other path treats a missing broker as `kite` (`(t.broker ?? 'kite')`). Restored rows normally carry a broker (`bookkeeping.ts:1722` defaults to kite), so this is an inconsistency, not a known live gap.

### 17. LOW: after a restart `reconcileFromTrades` maps a paper row to Kite, and `cancelProtection` is not persisted

- `reconcileFromTrades` infers the broker as `ant`, `prism`, `kite` or `breeze` from `trade.broker`, else from order-number fields, else `kite` (`exitMonitor.ts:232-236`). A `paper` row with a target/stop (set by `setTargetStopLoss`, which writes the fields on any row) is registered as an active Kite watch. Its exit then fails with "no tracked open trade" (the Kite lookup filters to `broker === 'kite'`) and retries at the 60 s cap with an ALERT each time; no paper exit is enforced either way.
- `cancelProtection` clears `trade.gttTriggerId` in memory only (`attachProtection.ts:73`), while the Buy document keeps the id written by `persistGttTriggerId`. After a restart the deleted GTT id is restored; the GTT poll then finds it missing for 3 polls and falls back to an active in-app watch (`kiteExecutor.ts:962-975`), which re-arms the target/stop the caller cancelled.

## Items checked and found sound (no finding)

- Mirror recursion: excluded at `eligibleUser`, `onUserSell`, `mirrorSetTargetStopLoss`; admin legs are never re-mirrored.
- Force-close double sell: sweep and drawdown handler share `forceCloseStartedAt` (keyed by the Trade row) and `shortCloseKey`; a failed attempt releases at once, a successful one is held until the row leaves `trades` or 2 min pass; cancel-race fills are subtracted once with the two-view minimum and the order is awaited out of the resting set (`waitUntilNotResting`).
- Per-user gate: `withUserGate` is FIFO and releases in `finally`; `reconcileInFlight` is awaited by every buy and by squareOff, chunked squareoff, `openTrades`, `canPlaceOrder`, `contractHolders`, `platformSells`, protection and butterfly close verbs. (The gate's side effect is finding 18 below.)
- Locked sells: durable ledger, day-keyed, bounded to 5 replacements, one handler per order id (`forget` before re-placing).
- Foreign-sell watch scheduling: settle/window/serial-per-broker logic is consistent; errors do not wedge a key.
- Restart: `restoreFromMongo` returns the cached startup result only when it was ok, otherwise re-runs; exit monitor is rebuilt from `bookkeeping.trades` after both the restore and every EOD run; the DataLink replays active subscriptions on connect, so subscribing before `connect()` is safe.

### 18. MEDIUM (side effect of finding 1's mechanism): an on-demand sync blocks every protective order request for its whole duration

- Evidence: `runEodRepair` sets `reconcileInFlight` to its gate (`orderProcess.ts:1594-1595`) and holds it until all four brokers have been repaired one after another (`:1576-1580`), plus an extra poll per tracker (`:1582`). While it is set, `placeOrderWithPendingGuard` (`:378`), `squareOff` (`:905`), `chunkedSquareOff` and `chunkedSquareOffLimit` (`:965,975`), `butterflyCloseLeg`, `antPlaceLimitSellBare`, `brokerPlaceLimitSellBare`, `sellContract`, `attachProtection`, `openTrades` and `canPlaceOrder` all wait. Nothing bounds the gate: `eodRepairBroker` makes several broker reads per broker (ANT reads 3 s apart for confirmation, `bookkeeping.ts:2759-2779`) and the loop has no overall timeout. The exit monitor and `forceCloseTrade` do not wait, so only strategy-issued exits and manual UI exits are held.
- Failure scenario: feature.md line 21 says the sync "runs at any time of day". At 10:30 the operator runs `npm run sync`. For the length of the run (tens of seconds, longer if a broker call stalls to its own timeout) a strategy's stop-loss or hedge sell sent through IPC waits behind the sync, and a buy is blocked.
- Fix direction: give the intraday run a deadline, or make the sell-side verbs not wait for the gate (they already size from live broker positions).
