## Findings

### F1 (HIGH) TargetReach has no persisted "fired" state: a restart while enabled buys again
TargetReachStrategy.ts:21 (`fired` in memory), :36-37 (constructor `ensureArmed`), :91-102.
The strategy fires once per process, then keeps `enabled: true` in config.yml (it never disables its block, unlike TopStock and Recommendation). After any restart (hot restart, crash, deploy) `fired` is false, `ensureArmed` re-subscribes the contract, and the first tick with `ltp >= targetPrice` buys the contract again. Scenario: target price 150 reached at 10:12, buy filled with GTT; process restarts at 11:00 with the option still at 160; a second buy of `quantity` (1755 in the config block) is placed on the first tick. Nothing here checks the existing position. Any gate in `canPlaceOrder` is the only brake, and it is not specific to this strategy.
Also: `targetPrice: 0` (the shipped value) with `strike` set fires on the first tick, since `ltp >= 0`; `ltp >= undefined` does not fire. The check is a level test, so a contract already above the target when armed buys immediately, not "when it crosses".
Also: a resolve failure sets `this.enabled = false` in memory only (:73), an in-memory-only control that config.yml does not show (CLAUDE.md rule).

### F2 (HIGH) Butterfly: a SELL leg whose order outcome is unknown is never adopted; a live short is left unmanaged
ButterflyStrategy.ts:282-298 (`placeSellLegs`), :300-317, compare :392-394 (`unwindPartialEntry` does call `adoptUnknownOutcomeLegs`).
When `butterflySellToOpen` throws a timeout/transport error, the leg is parked as `status 'error'`, `filledQty 0`. `placeSellLegs` only buys back legs whose promise was fulfilled, sets `phase = 'error'` and returns, without calling `adoptUnknownOutcomeLegs`. If that sell actually filled at the broker, the short is live with no leg status 'open', so no tick exit, no EOD close, and `phase 'error'` is never auto-retried (:758-759). The standard-mode wings stay open too (F3), so the book is long wings plus one short centre, unmonitored. The same gap exists in `resumeOrPlaceSellLegs` (:362-366, which is also dead code, F13).
Fix direction: call `adoptUnknownOutcomeLegs(pos)` before deciding which sells to buy back, as `unwindPartialEntry` does.

### F3 (MEDIUM) Butterfly: failed sell step leaves the two long legs open, unmanaged; feature.md says "unwind on partial entry"
ButterflyStrategy.ts:279-298. The comment states the wings are left "open flagged for manual review". Status stays `'open'` but `phase = 'error'`, so `processOptionQuote` (:446) skips the position and `eodCheck` (:567) only closes `phase 'open'`. Scenario: sell leg 1 is rejected by `canPlaceOrder` (the gate runs again for sell-to-open, `placeOrderWithPendingGuard`, orderProcess.ts:1102-1107, and R05 #6 notes the gates test "already at cap"). The wings bought moments earlier then sit as long options to expiry/EOD with no stop. Contrast with a failed BUY step, which unwinds the long that filled (:254-260,397-402). The two paths are inconsistent. Reverse mode: the same applies to the long centre legs.

### F4 (MEDIUM) Butterfly: closing one broker's combo unsubscribes the shared token for the other broker
ButterflyStrategy.ts:425 (`unwatchTokenOnSource('ant', leg.token, this, leg.exchange)` in `closeOneLeg`), tokenRouter.ts:143-150 (watchers are a Set of strategy objects per token, not per broker).
One instance fans out to several brokers (`brokers: [kite, ant]`) and every leg token is the ANT-native token, identical across brokers for the same strike. When broker A's leg closes, the single `(token, strategy)` watch entry is removed, so broker B's still-open legs on the same token stop receiving ticks. `canHandleOptionQuote` (:433) is then never asked about that token; B's combo has no target/stop/stale-price protection until the EOD close at 15:15 (which also runs from index ticks, so it still happens). Scenario: A hits stop at 11:00 on a quiet leg, closes, B's leg ticks stop; B loses -40 points before EOD. Current config uses one broker per Butterfly block, so it is latent. Fix direction: unwatch only when no other broker position uses the token.

### F5 (MEDIUM) Butterfly: reconcile adopts the broker's net position by tsym with its sign discarded
ButterflyStrategy.ts:657-667 (`Math.abs(getLiveQuantity)`), :669-700 (`filledQty = liveQty; closedQty = 0`), :335-338.
The live quantity is the net position of that tradingSymbol at the broker for the whole account/user, not this combo's own. If another strategy or the user holds the same ATM strike (a Continuous/Expiry long, or the user's own Kite position, see memory "Manual Kite orders"), the restart close sells/buys back that whole quantity, and `Math.abs` means a net-long that should have been a short is bought again (adds exposure instead of closing). Combined with `restoreAction` closes running from ticks, this can close or increase unrelated positions. Same sign-less `adoptUnknownOutcomeLegs` (:381-385).

### F6 (MEDIUM) Recommendation: reverse on SENSEX uses a NIFTY quote and a 50-step strike
RecommendationStrategy.ts:224-239 (`runReverse(cfg, key, quote)`, `atmStrike(quote.ltp)` with default step 50, recommendationCycle.ts:75), LimitEntryStrategy.ts:643-646 (only `processNiftyQuote` is wired).
With `index: SENSEX` the tick that drives the strategy is a NIFTY tick, so the reverse leg's strike is the NIFTY level (about 25,700) rounded to 50 on the SENSEX chain (about 83,000, step 100). The contract lookup fails, or the order is refused, and the reverse of a profitable trade is lost; with a wrong-but-listed strike it would buy a far-ITM/OTM SENSEX option. Scenario: `repeat: false, reverse: true, index: SENSEX`, first trade hits target, option falls back to entry, reverse fires on a NIFTY tick. No guard rejects `reverse` with SENSEX.

### F7 (MEDIUM) Sentiment: a failed or refused averaging/sell order leaves `orderPlaced = true` forever
SentimentStrategy.ts:88-96 (averaging buy not awaited, return value ignored), :100-107 (sell), :119 (only a Buy fill clears `orderPlaced`).
`orderPlaced` is set before the call; `Strategy.buyContract` swallows errors and returns null (strategy.ts:191-206). A refused or timed-out average buy therefore never clears the flag, which also blocks the target sell (:102-103 requires `!orderPlaced`). The position then has no strategy exit; only the entry's `buyIndex` GTT (if any) covers the first lot. The same happens for a rejected target sell: no retry. Scenario: price drops 40 points, the add-on is rejected for margin; the contract recovers to target; no sell is ever sent.

### F8 (MEDIUM) Sentiment: any Sell fill clears the whole contract, even a partial sell; entry GTT plus own sell can double-sell
SentimentStrategy.ts:135-139 (`clear()` on every Sell), :215 (entry via `buyIndex` with `targetPoints`, so the order process attaches a target exit), :100-106 (strategy also sells at target), :95 (averaging buys go through `buyContract`, not covered by that exit).
(a) The entry GTT covers only the first buy's quantity; after averaging, its Sell fill clears the contract and sets `ordered = false` (:253), so the next loop buys again while the averaged remainder is untracked. (b) The GTT target and the strategy's own target sell can both fire on the same price move; the second is only stopped by the order process's never-short guard, not by this code. (c) A chunked or partial sell is treated as complete.

### F9 (MEDIUM) TopStock: code uses a 09:10-09:20 window; feature.md says "at first tick"; stale comments describe other windows
TopStockOptionsOpeningGapStrategy.ts:52-53 (`TRADING_WINDOW_START 9:10`, `END 9:20`), :163-175 (`isTimeInRange` gate in `processNiftyQuote`), comments :421-423 ("10:10-10:35 window") and :18-30.
Memory note topstock_first_tick.md records the user's rule that the strategy fires on the first tick, not a 9:10-9:20 window. The code does not do that: a process that starts at 09:21 or later never trades that day, a day with no NIFTY ticks inside 09:10-09:20 is skipped, and at 09:10-09:14 `getOpenAndPrevClose` may return pre-open data (`open` is zero/missing before 09:15, retried every 15 s, :293,:185). Either the code or feature.md/memory is wrong; the user needs to decide which. The comments at :18-30 and :421-423 describe two further, older windows.

### F10 (MEDIUM) TopStock: `reset()` does not call `super.reset()` and cannot re-arm the day
TopStockOptionsOpeningGapStrategy.ts:230-234. Sets `phase = 'idle'` only. `hasFiredToday()` (file marker, :138-145) is still true so the next tick sets `phase = 'done'` (:176-180); the admin reset has no effect, and since `durablyDisable` also set `enabled: false` the operator must flip config.yml by hand and delete the dot-file. Not calling `super.reset()` also skips the global max-profit latch clear (R07 F11 already lists this); the file-marker angle is new.

### F11 (MEDIUM) GoodMorning: no automatic previous close; Sensex block cannot trade as shipped
GoodMorningStrategy.ts:187-192, GoodMorningSensexStrategy.ts:153-158, config.yml:117-136.
`previousClose` comes only from config. The NIFTY block carries 24219 (a stale constant); the Sensex block has no `previousClose`, so every day logs "config.previousClose not set - skipping today" and sets `traded = true`. Also the Sensex block carries unused keys `targetPrice`, `cooldownSeconds`, `driftCancelPoints` (not read by the strategy; grep returns no match in GoodMorning*.ts), and `minMovementPoints` falls back to 30 for SENSEX. feature.md's "09:15 vs previous close" implies an automatic previous close; it is a manual input.

### F12 (MEDIUM) Gap, RateOfChange, Sentiment, GoodMorning: day state is in memory; a restart re-enters, an open position loses its strategy exit
GapStrategy.ts:105-106 (`decidedToday`), :96 (`contract`); RateOfChangeStrategy.ts:114; SentimentStrategy.ts:146-149; GoodMorningStrategy.ts:37-43. None has `reconcile()` or a persisted marker (compare RuleBased's reconcile and TopStock's file marker).
- Gap: restart between 09:10 and 09:25 after the trade resets `decidedToday`, and `buyIndex` is called a second time. (The GTT bracket remains for the first entry; the timeout exit is lost.)
- RoC: after a restart `contract` is null, the position's timeout sell is gone, and the next velocity signal opens a second position on top.
- Sentiment: `iterationCount` and `ordered` reset, so it opens a new loop with the old position still held and its average/target logic gone. `iterationCount` also never resets on a new day (no `resetIfNewDay`), so a process left running overnight stops after `loopCount` total entries.
- GoodMorning: a restart within 2 minutes of a re-armed snapshot window retakes the snapshot from the current price (:180-207), changing the baseline; a restart after the trade is skipped only because of `LATE_WINDOW_MINUTES`.
Whether `canPlaceOrder` limits the second entry depends on the user's caps; nothing in these files does.

### F13 (LOW) Butterfly: dead code and fragile config/limits
- `resumeOrPlaceSellLegs` (ButterflyStrategy.ts:327-367) has no caller (grep: only its definition).
- `targetPoints`/`stopLossPoints` NaN: `netPoints >= NaN` and `<= -NaN` are always false, no exit would ever fire; `validateConfigFile` requires the keys but its numeric check is not verified here (configValidation.ts:336).
- `configuredBrokers()` returning an empty list leaves `phase = 'running'` with no positions and the day's cycle count used (:149-161); only a restart's reconcile clears it.
- A position left in `phase 'error'` keeps `isRunning()` true and the strategy never re-idles (by design, "until a human clears it"), but the admin reset (:771-784) then drops the live-leg tracking with only an ALERT.
- `getLiveQuantity` keys by tsym only; for the two brokers sharing a user id this is the broker-scoped call, fine.

### F14 (LOW) TopStock: ranking includes stocks without options, and the nearest expiry may be today
TopStockOptionsOpeningGapStrategy.ts:289-314 (ranks all resolved cash tokens), :350-354 (non-F&O stock skipped after ranking), AntContractMaster.ts:229-236 (expiry >= today).
`rankStart: 3, rankCount: 2` selects slots 3-4 of the full ranking, so a Nifty Next 50 stock with no listed options in the window yields no leg and the slot is not refilled by the next ranked stock. On a monthly stock-expiry day the nearest expiry is today's, and the position is bought with `LONGTERM` (overnight) and a resting sell, i.e. it is held into settlement. Unverified: whether Kite/Breeze product for `butterflyBuyLeg` is intraday or overnight.

### F15 (LOW) RuleBased / RateOfChange: partial exit handling and zero-quantity
- RuleBasedStrategy.ts:130-137: a strategy-placed exit is booked complete on the first Sell fill; chunked exits (freeze limit) clear the contract with quantity still held, while the non-strategy exit branch at :141-151 does handle chunks. Default quantity 65 does not chunk.
- RuleBasedStrategy.ts:209-214: `quantity ?? 0` is passed to `buyContract` without a check.
- RateOfChange: a failed timeout `sellContract` leaves `sellOrderPlaced = true` (:55-59), so no retry; `numberOfDatapointsReceived > 50` makes `getRecent(2N)` shorter than 2N (history is capped at 100), so acceleration is always 0 and it never trades; no daily trade cap (each close re-arms).
- Gap: `squareOff` timeout uses a hard-coded `exchange: 'NFO'` (:60); fine for NIFTY, wrong if the block is ever used for SENSEX.

### F16 (LOW) GoodMorning retry/rearm rewrite config.yml wholesale
GoodMorningStrategy.ts:119,149; GoodMorningSensexStrategy.ts:115; goodMorningRetry.ts:52-58. Each retry, rearm and next-day recovery calls `writeConfig(getConfig())`; R07 F1 (config writes rewriting Expiry's `maxProfit`) and F12 apply, and a hot-reload race with an operator edit is possible. Not new in kind, noted because these strategies write at 09:20-14:45 during market hours.

### Verified OK (no finding)
- Butterfly entry is serialised: `phase = 'running'` and `cyclesToday++` are set before any await and persisted (:153-155); `maxCyclesPerDay` survives a restart (:629).
- Butterfly closes shorts first and the longs only if every short closed (:504-511), and live-checks before every reconcile close (:669-700).
- Butterfly reconcile never trades (defers to `runPendingRestoreActions`, 15 s throttle, inside the trading window).
- Butterfly ticks use the stale-price alert but not the stale value as "unknown" (documented choice, :476).
- Gap uses a one-per-day decision, bad-tick guard (`prevClose > 0`) and PCR fail-closed.
- RoC/RuleBased/Gap set the entry sentinel before the first await (no concurrent double entry within one process).
- RuleBased entry failure releases the lock only after `getOpenTrades` confirms nothing is held (:398-424).
- Recommendation: key-per-day persisted (not re-placed across restarts), band refusal stays enabled, `adjustOpenTrade` refuses unbracketed levels.
- TopStock: `recordFiredToday` before any order, not executing if the write fails (:149-157,430). Timezone is pinned in orchestrator.ts:6 (`./util/tz`), so `moment()` windows are IST.
