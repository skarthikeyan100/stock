## Findings

### 1. HIGH - Breeze manual reconnect leaves the feed dead while logging "Connected and streaming"
- `BreezeDataStream.reconnect()` (BreezeDataStream.ts:341-345) calls `disconnect()` -> `Breeze.wsDisconnect` -> SDK `self.socket.disconnect()`, then `connect()` -> `Breeze.wsConnect` (Breeze.ts:224-232) -> SDK `self.wsConnect`.
- SDK `breezeConnect.js:219-224`: `wsConnect` only creates a socket `if (!self.socket)`; `self.socket` is set once (line 66), initialised null (line 25) and is never set back to null on `wsDisconnect` (lines 226-229) or anywhere else. So the second `wsConnect` is a no-op: the old socket stays manually disconnected (socket.io does not auto-reconnect a client-initiated disconnect) and its `auth` (userId/sessionKey captured at line 66-69) stays stale.
- `connected = true` is then set and "Connected and streaming" is logged (BreezeDataStream.ts:277-278).
- Scenario: Breeze session exists at startup, socket connects, ticks flow; user re-logs in (frontend sends `reconnect` for source breeze, dataProcess.ts:70-75) or a manual /breeze reconnect is issued. The feed is silently dead; Breeze legs get no ticks. The stall watchdog only calls `subscribeFeeds` (a `socket.emit` on the dead socket) every 30 s/3 min.
- Not affected: the very first connect after a login when no earlier `wsConnect` happened in this process.

### 2. MEDIUM - Breeze ticks are amplified N times (duplicate `stock` listeners), growing every heartbeat
- SDK `watch()` (breezeConnect.js:144-150) does `self.socket.on('stock', self.onMessage)` on every call, including repeats for the same token. `@socket.io/component-emitter` `on` (node_modules/@socket.io/component-emitter/index.js:40-45) pushes without de-duplication; the SDK never calls `off`.
- `BreezeDataStream` calls `subscribeFeeds` for each `subscribeOption`, each socket (re)connect (:248-251), each watchdog resubscribe (:312-316) and every 3 minutes per token via the heartbeat (:331-339). The comment at :322-327 says resubscribing has "no duplicate-tick side effects", but that was only observed server-side.
- Failure scenario: 3 Breeze tokens, 6 h session = 360 heartbeat resubscribes + others, so after N `watch()` calls each incoming tick runs `onMessage`/`parseData`/`emitTick`/`writeTick` N times and N identical JSON lines go to every data client. CPU and socket backlog grow with time (the 32 MB slow-client drop in DataServer then silently drops ticks of every type).

### 3. MEDIUM - Breeze server-initiated disconnect / auth rejection is never recovered; code comment is wrong
- BreezeDataStream.ts:247-253 only logs `disconnect` and `connect_error`; BreezeDataStream.ts:347-348 states "Once the socket exists, socket.io reconnects it".
- breezeconnect uses socket.io-client 4.7.2 (node_modules/breezeconnect/node_modules/socket.io-client). In v4 a `disconnect` with reason "io server disconnect" and a `connect_error` raised by server-side auth middleware are not auto-reconnected (documented client behaviour; not exercised here). `connect()` reports success regardless (:277), and `connectWithRetry`'s retry only covers `hasValidSession()` failures.
- Scenario: Breeze server drops the socket (session expiry, duplicate login). `connected` stays true, no retry is armed, the watchdog resubscribes into a dead socket forever.

### 4. MEDIUM - ANT feed has no tick-silence watchdog / resubscribe (index or option tokens)
- AntWebSocket watchdog (AntWebSocket.ts:79-84) counts any message or pong as liveness, so a subscription that is silently dropped by the broker while the socket is alive is never detected. Breeze has a per-token stall watchdog (BreezeDataStream.ts:301-320); ANT has none.
- `checkFutSilence` (AntDataStream.ts:294-301) runs only from the NIFTY branch of `emitTick` (:303-318 area), so it cannot fire when NIFTY itself stops; it alerts for the future only while NIFTY keeps ticking.
- strategiesProcess `feedDown` (strategiesProcess.ts:463) only reacts to the data socket closing.
- Scenario: ANT stops sending ticks for NIFTY/option tokens but still answers pings; nothing alerts, nothing resubscribes, open legs are tick-blind. (The EOD clock poke at strategiesProcess.ts:298-306 only helps EOD.)

### 5. MEDIUM - Support/resistance SEEKING never confirms the window unless a tick lands exactly `confirmWindowMs` earlier
- lib/supportResistance.ts:115-118: buffer is filtered to `t.ltt >= cutoff` (cutoff = tick.ltt - confirmWindowMs) and then `spanReached` requires `tick.ltt - buffer[0].ltt >= confirmWindowMs`. After the filter `buffer[0].ltt >= cutoff`, so the condition holds only if `buffer[0].ltt === cutoff` exactly; ticks older than the window, which would prove the span, were just discarded.
- Reproduced (confirmWindowMs 60000, flat range): ticks every 1000 ms exactly -> locks on tick 60; ticks every 1000 ms with 0/100/200 ms jitter -> never locks in 400 ticks; every 700 ms -> never; every 1500 ms -> locks at tick 40.
- With ANT `ft` (whole seconds, SupportResistanceStrategy.ts:146-151) it locks only when a tick exists at exactly T-60 s: lock is delayed or skipped on sparse/irregular seconds. With ms timestamps (replay/backtest) it effectively never locks.
- Strategy is `enabled: false` in config.yml:141, so no live impact today.

### 6. LOW-MEDIUM - ANT connect-fail ack (`cf`) is treated as an open
- AntWebSocket.ts:95-97 triggers `open` for both `ck` and `cf`; AntDataStream's `open` handler (AntDataStream.ts:103-114) then subscribes, and `connect()` has already resolved on socket open (AntWebSocket.ts:86-87) so `connected = true`, backoff reset (:150-152).
- Scenario: auth token rejected with `cf` while the TCP socket stays open: heartbeat/pong keep the watchdog quiet, no reconnect/relogin path runs, no ticks arrive (compounds #4). Whether the server closes the socket after `cf` is not verified.

### 7. LOW-MEDIUM - Live 300 s stats builder is unaligned, unseeded and unpersisted
- niftyStatsBuilder.ts:167-169: the module-level builder is non-aligned (bucket start = first tick seen, drifting), has no `seed`, and nothing persists its closes (aligned builders in NextWeek/GammaBurst seed from Mongo/Yahoo). niftyQuoteHistory is also process-local (niftyQuoteHistory.ts:9-10).
- Scenario: strategies code change -> hot restart mid-day: closes are empty, so RSI(14) (needs 15 closes = 75+ min), MACD, Bollinger etc. return null until enough new candles accumulate, and candle boundaries are re-anchored to the restart tick.
- Also the first candle after restart is whatever ticks arrived; indicators using drifting (>=300 s) candles are not comparable with pre-restart ones.

### 8. LOW - ADX and Stochastic are computed from closes only in the live pipeline
- niftyStatsBuilder.ts:113-128 passes `closes` as highs and lows (acknowledged in a comment). ADX true range becomes |close - prev close| and Stochastic %K uses close range, so values differ from the standard indicators the name implies (`lib/indicators.ts:285-390` is correct given real highs/lows). No live config.yml block references `ADX_`/`Stoch_` today; used by ruleIndicators/backtests only.

### 9. LOW - Flat prices give RSI = 100 and a directional trend
- indicators.ts:136 (`avgLoss === 0` -> 100, so 'DOWN' when overbought threshold < 100) and indicators.ts:169-171 (reversed: flat -> 'UP'). With avgGain and avgLoss both 0 the value is undefined, not 100. Scenario: a flat/seeded sequence (e.g. seed candles with identical closes, or a halted feed) emits a spurious RSI signal.

### 10. LOW - NiftyQuote prevClose cache seeded from a rounded `pc` and never reset per day
- model.ts:50-65: `lastPrevClose` is a static Map seeded once per token from `ltp / (1 + pc/100)` where `pc` is rounded to 2 decimals (up to about +/-1 point error on ~24000, constant for the day) and never invalidated. If the data process spans more than one session, change/changePercent stay anchored to the first day's value. Whether the data process is ever kept running overnight was not verified (orchestrator does not restart it, orchestrator.ts:277-279).

### 11. LOW - Weekly momentum ranking distortions
- weeklyMomentum.ts:188-190: `avg(...) || 1` replaces a missing early/late half with 1. A symbol with data only in the late half gets volumeRatio about 1e6 (volume/1) and tops the ranking; one with only early data gets about 1e-6. Scenario: one missed daily fetch for a constituent or an index change.
- fetchDaily.ts stores `totalTradedVolume` as returned at fetch time; if run during the session it is partial-day volume and the ratio depends on fetch time (the date guard at :29 only skips a stale-dated response, and a null `lastDataDate` stores anyway).
- weeklyMomentum.ts:95-96 uses `moment()` in host TZ (script does not import util/tz).

### 12. LOW - Future VWAP feed edge cases
- AntDataStream.ts:229-233: on a `futToken` change only the first-tick flags are reset; `futVwap` (own sums, `ap`, volume) is not, so a mid-process roll would mix old and new contract state until `v` goes backwards (own VWAP resets, `ap` stays until a new one arrives). Roll only happens on (re)connect (resolveFuture is called from `open`).
- `lastFutAlertAt` (:258-261, :297) is shared by the issue alerts and the "no fut tick" silence alert, so a stream of `ap-is-zero` issues suppresses the silence alert for 5 minutes.

### 13. LOW - feature.md claims not fully matching code
- "PCR (+/-300-point window)": BulkPcrStrategy.ts:913 uses 3x (900 points) for SENSEX; other callers use 300.
- "Mongo NiftyQuote/SensexQuote": `persistQuote` also writes OptionQuote documents for dynamic/depth tokens (AntDataStream.ts:335-337).
- "NSE client" is the puppeteer scraper (momentum/nseClient.ts); src/nse_index.ts is an expiry/strike helper, not a data client.

### 14. LOW - ANT reconnect backoff never grows for connect-then-drop flapping
- AntDataStream.ts:150-152 resets `reconnectDelayMs` to 2 s on every successful connect, and the `close` handler path (:126-136, :185-188) uses that delay without doubling. A socket that connects and drops immediately (e.g. the server accepts then closes) reconnects every ~2 s, each time running `getSessionId`/`prepareWsSession` (HTTP) against the broker.

### 15. LOW - DataServer.start unconditionally unlinks an existing socket path
- DataServer.ts:35 `fs.unlinkSync(socketPath)` without checking whether another live `data` process owns it; a second instance would silently take over (the first keeps ticking to nobody). `ownSocketTracker` only protects the unlink on shutdown.
