## Findings

### F1 (HIGH) Any config write turns ExpiryStrategy's rupee `maxProfit` into `"N%"`, which the validator then rejects
- `ConfigService.writeConfig` runs `formatPercentFields` on every block (prism/ConfigService.ts:72-73). `formatPercentFields` skips `maxProfit` only for `type === undefined | SimpleContinuousStrategy | ScaledHedgedStrategy` (prism/percentConfig.ts:79). `maxProfit` is in `PERCENT_KEYS`.
- ExpiryStrategy's `maxProfit` is rupees: capForBlock treats it as rupees (processes/strategies/globalMaxProfit.ts:34-35 `RUPEE_BLOCK_MAX_PROFIT`) and validation requires a number (prism/configValidation.ts:409). config.yml:452 currently has `maxProfit: 20000` on the Expiry block.
- Reproduced: `formatPercentFields({type:'ExpiryStrategy', maxProfit:20000})` returns `{"maxProfit":"20000%"}`.
- Scenario: any `POST /config` (routes/admin.ts:116) or any strategy self-write of its block (ConfigService.mergeIntoFile path) while the Expiry block is enabled writes `maxProfit: "20000%"` to config.yml. The reload then fails validation (configValidation.ts:409 sees a string, line 316-322 validates enabled blocks), `loadConfig` keeps the previous config (ConfigService.ts:121-126) while `POST /config` still answers 200 (admin.ts:139). On the next process start `loadConfig` throws (ConfigService.ts:123) and the platform does not start. Same class as the 2026-11-11 incident noted in percentConfig.ts:75-78.
- Also: the monitor then never sees the file change again (all later edits to config.yml are rejected as a whole, see F12).

### F2 (MEDIUM) LimitEntry family state file: non-atomic write, and a parse error is treated as "no state"
- `save()` uses `fs.writeFileSync(stateFile, JSON.stringify(state))` in place (strategy/LimitEntryStrategy.ts:183): no temp+rename, no fsync (ConfigService does it properly, ConfigService.ts:75-90). `ensureLoaded` wraps the read in `catch { /* no file yet */ }` (LimitEntryStrategy.ts:175), so a truncated or corrupt file silently yields `{keys:[], legs:{}}`.
- Scenario: crash / disk-full during the write of `.ExpiryStrategy.<id>.json` (or the other LimitEntry-family files). After restart the strategy has no cycle keys (a slot already fired today fires again: duplicate entry) and no legs (filled positions untracked; reconcile only adopts quantities the order side holds, :803-817, with no exit until ticks place one). Applies to Recommendation, NiftyChange, MomentumAtFixedTime, NextWeek, Breakout, GammaBurst, HighLow, Expiry.
- Distinguishing ENOENT from a parse/IO error and failing closed (refusing to trade) is not done.

### F3 (MEDIUM) Transient in-flight markers are persisted and never cleared on load: `exitRetryAt === -1` and `closing: true`
- `entryComplete` sets `leg.exitRetryAt = -1` (LimitEntryStrategy.ts:977) and the leg is saved by later `save()` calls inside placement; `closeLeg` sets `leg.closing = true` (:1066) and a fill-driven `save()` while the close runs persists it. `ensureLoaded` (:159-178) and `reconcile` (:744-820) never reset either.
- After a restart: `entryComplete` returns on `exitRetryAt === -1` (:976) and housekeeping requires `exitRetryAt !== -1` (:1119), so a filled leg with no exit never gets one. A leg with `closing: true` is skipped by the tick stop (:662, 669), the exit/top-up (:912, 922, 1118) and the EOD close (:1122, 1063).
- Scenario: restart (HOT_RESTART or crash) between the first chunk fill of a close and the second; the remaining lots stay unmanaged until by hand. No ALERT is logged for this state.

### F4 (MEDIUM) Exit placement is abandoned after 10 attempts (~5 min) and the position stays without target or stop
- `tryPlaceExit` sets `exitRetryAt = Number.MAX_SAFE_INTEGER` at `MAX_EXIT_ATTEMPTS = 10` with 30 s back-off (LimitEntryStrategy.ts:39-40, 990). The attempt counters are persisted, so a restart does not retry either. The only remaining exit is the EOD `closeLeg` (:1122).
- Scenario: broker/ATTACH/limit-sell refusals for more than ~5 minutes (e.g. a Breeze funds/limit rejection) leave a filled position with no stop for the rest of the day. One ALERT is logged, no operator control re-arms it except `dropExit`-style code paths not reachable from config.

### F5 (MEDIUM) Startup reconcile does not retry a failed strategy, and LimitEntry.reconcile swallows its failure
- strategy.ts:41 and strategiesProcess.ts:484 state a strategy whose reconcile threw "is retried" / "retries until it succeeds". Code: `startupReconcile` calls `runReconcile()` once and `return`s even when `pending.length > 0` (strategiesProcess.ts:190-194). A strategy whose `reconcile()` threw stays `stateLoaded=false` (:168-170) and receives no ticks, fills or cancels (so no tick stops, no EOD close) until a manual `POST /reconcile`.
- Opposite problem: `LimitEntryStrategy.reconcile` catches the `getOpenTrades` failure and `return`s normally (LimitEntryStrategy.ts:747), so `stateLoaded` becomes true although nothing was reconciled (lost-fill adoption and close detection skipped).
- Scenario A: one Mongo/IPC blip during startup reconcile of one strategy with an open position: that position has no managed exit all day, no automatic retry. Scenario B: the reverse for the LimitEntry family.

### F6 (MEDIUM) A removed block / removed broker is not disabled by hot reload, and the instance then runs on another block's config
- `Strategies.loadExpandedConfigs(true)` only iterates configs that still exist and sets `enabled` from them (strategy/strategies.ts:38-44). An instance whose block or `brokers:` entry was removed keeps its previous `enabled = true`, stays in `this.list`, and keeps receiving ticks (`receivesEvents` only reads `enabled`, strategy.ts:47).
- `instanceConfig()` then finds no expanded config and falls back to `configService.getStrategyConfig(getClassName())`, the FIRST block of that type (strategy/strategy.ts:104-115), which for a `-ANT` instance is the kite block (different `maxInvestment`, brokers, enabled).
- Scenario: operator removes `ant` from `brokers: [kite, ant]` to stop trading on ANT; the `X-ANT` instance keeps trading on the kite block's settings until a restart. (POST /config guards block removal, admin.ts:111-115, but a `brokers:` edit or a direct file edit is not guarded; CLAUDE.md says controls live in config.yml and must take effect.)
- Also noted in strategies.ts:61-64: a block ADDED at runtime gets no instance until restart (silent: the new block never trades).

### F7 (MEDIUM) Enabling a strategy at runtime does not force a reconcile; a disabled strategy has missed every fill
- `refreshFromConfig` copies `enabled` only (strategies.ts:41-44); `stateLoaded` stays true from startup. While disabled, fills and cancels are dropped (strategiesProcess.ts:68-71, 134-137) and the `openQty` / `registerTrade` net bookkeeping for that fill is skipped too (the early return precedes it).
- Scenario (the lock-profits case described in platformSells.ts:6-9): strategy disabled, order process sells its legs; config flips back to `enabled: true`; the strategy resumes on a stale 'filled' leg with a tick stop / EOD close and attempts to sell lots already sold (never-short refusal loops, one ALERT per back-off) and books no P&L. The comment at strategiesProcess.ts:66-67 relies on the operator remembering `POST /reconcile`.

### F8 (MEDIUM) 15:25 to `eodCloseTime` gap: no ticks, fills or cancels reach strategies, and dropped fills are never replayed
- Window ends 15:25 (util/marketHours.ts:3-4, 93-98); the event window opens only at `eodCloseTime` (util/eodClose.ts:38-44). config.yml:21 has `eodCloseTime: '15:30'`, so 15:25:00-15:29:59 is dead: tick-driven stops/targets, LegManager square-off / max-profit and EOD logic do not run, and any fill (a resting target sell) in that gap is dropped by `onFill` (strategiesProcess.ts:68-71) without updating `openQty` or the strategy.
- Scenario: a resting target sell fills 15:27; the leg stays 'filled'; at 15:30 `closeLeg` runs against lots already sold (LimitEntryStrategy.ts:1075-1078), the never-short guard refuses, the leg never reaches 'closed', P&L outcome never recorded (only a restart's reconcile repairs it).

### F9 (MEDIUM) LegManager's own maxProfit is session-scoped, not day-scoped; latch persistence and load are weaker than PnlStop's
- `realizedPnL` starts at 0 in each process and is only incremented in-process (strategy/LegManager.ts:448, 999, 1008); no restore path sets it. `computeCumulativeProfit` = `realizedPnL - maxProfitBaseline + unrealized` (:671-673). After a restart (HOT_RESTART, deploy) profit already made today is forgotten, so the cap is re-measured from the restart. The latch itself does survive (:767-778). Feature.md line 94 says "survives restart" about the global latch only; Continuous/SupportResistance rely on this class.
- `persistProfitState` / `persistLossState` / `persistLatch` write once, fire-and-forget (LegManager.ts:755-763, 832-838, 872-883); PnlStop.persist retries twice (strategy/PnlStop.ts:170-182). `loadPersistedLatches` fails OPEN on a read error (LegManager.ts:787-789: "continuing with the stop untripped") whereas PnlStop.load fails CLOSED (PnlStop.ts:130-135).
- Scenario: Mongo blip at trip time or at restart: a tripped max-profit / max-loss lockout is lost and trading resumes after the mass close.
- Related behaviour, not a bug: when `settings.maxProfit` applies to Continuous/SR via LegManager (`cfg.maxProfit == null`, :698-703) the trip mass-closes at market (:946-983), not "locks the cap with limit sells" as feature.md L94 reads for the global cap.

### F10 (LOW-MEDIUM) LegManager can double-count a partial own sell when its fill echo arrives after the leg is put back
- `sellLeg` on `PartialSellError` already reduces `leg.totalQuantity` and books P&L for `soldQty` (LegManager.ts:997-1002). The callers then put the leg back into `legsByToken` (:965, 1174, 1234). A late Sell fill for that same partial arriving after the put-back finds the leg tracked and is treated as an external partial sell (:1587-1594): quantity reduced and P&L booked a second time. The `ignoredSellEchoes` guard is used only for `sellBack`, not for `sellLeg`.
- Needs the partial's fill event to be delivered after the failed sell returns; during the sell await the leg is absent from the map and the echo is ignored (:1574). Not reproduced; stated from code reading.

### F11 (MEDIUM) Admin reset of TopStockOptionsOpeningGapStrategy does not clear the global max-profit latch
- `Strategy.reset()` clears it (`clearGlobalMaxProfit`, strategy.ts:131). TopStock's override does not call `super.reset()` (strategy/TopStockOptionsOpeningGapStrategy.ts:230-234), and TopStock is not in `OWN_MAX_PROFIT` (processes/strategies/globalMaxProfit.ts:20-22), so it is judged by the global monitor. Scenario: global cap trips for TopStock, operator calls `POST /strategies/TopStockOptionsOpeningGapStrategy/reset`; the order process keeps refusing its buys (bookkeeping.canPlaceOrder reads the latch) with the strategy reporting reset. Also `clearGlobalMaxProfit` is fire-and-forget (strategy.ts:131), and the order process caches the latch for 3 s (globalMaxProfitLatch.ts:40).
- BulkPcr's override (BulkPcrStrategy.ts:2973) also skips `super.reset()`, harmless only because BulkPcr is in `OWN_MAX_PROFIT`.

### F12 (LOW-MEDIUM) A rejected config file is silent to the operator and to the API; the previous config (including `enabled: true`) stays live
- `loadConfig` on any validation error logs and keeps the previous config (prism/ConfigService.ts:121-126). `POST /config` validates the posted flat config before writing but not the bytes actually written (formatPercentFields can change them, F1), then answers 200 (routes/admin.ts:116-139).
- Scenario: operator sets one strategy `enabled: false` in the same edit that contains a typo elsewhere; the whole file is rejected, the "disabled" strategy keeps trading, and the only trace is one log line. No in-process alert / status flag.

### F13 (LOW) globalMaxProfit monitor comment says a pre-existing resting sell is left alone, but it is re-priced after 20 s
- processes/strategies/globalMaxProfit.ts:99-101 adopts a pending sell with `price: 0` ("leave it, it is re-priced only by us"). On the next cycle `rec` exists, `keepTripSell(0, ...)` is false (maxProfitLock.ts:76) and `rec.at` is older than 20 s, so the code cancels every resting sell of the contract and replaces it (:92-97). Effect is the intended lock, but it also cancels a strategy's own resting target/stop sell placed earlier; comment and behaviour disagree.

### F14 (LOW) Global latch cache and fail-open read
- `latchGlobalMaxProfit` seeds only the `userId|broker` cache key (globalMaxProfitLatch.ts:21); a `userId|*` lookup cached as false stays false up to 3 s (:40, 46-49). A Mongo read failure answers "not latched" (:58-60); the monitor only re-asserts when the P&L is still over the cap (processes/strategies/globalMaxProfit.ts:44-50), so a latch lost to a read blip after profit was locked and realized under the cap is not re-asserted until the cap is reached again.

### F15 (LOW) SerialWriter timeout does not cancel the write
- On the 10 s timeout the chain moves on (strategy/SerialWriter.ts:22-30) but the original Mongo call is not cancelled; it can land after a later write and restore the OLDER snapshot, the exact reordering the class exists to prevent (its header comment, :3-8). Rare, needs a hung then recovering Mongo call.

### F16 (LOW) TrailStop arms immediately and never exits when activation is NaN
- `if (ltp < entry + activation) return hold` is false for NaN, so the trail arms on the first tick (strategy/TrailStop.ts:59-62); `exitLevel` is `Math.max(NaN, ...)` = NaN so `ltp <= level` never fires (:51, 70). `enabled()` validates only `trail` (:32-35), not `activation`. halfTrail passes `targetPrice - entry` (halfTrail.ts:41). Only reachable with a non-finite target price.

### F17 (LOW) LegManager reconcile edge cases
- `restoreFromOpenTrades` returns at once for an empty open-trades list (strategy/LegManager.ts:1670) without clearing `legsByToken`; on a manual `POST /reconcile` (not only startup) legs the order side no longer holds stay tracked (the 30 s broker verify covers only kite/ant, :309). A restored leg with no legLineage doc defaults to `isRoot: true` (:1715), so a nested hedge becomes a root and is refilled.

### F18 (LOW) feature.md L93 overstates the per-block override of the expiry-skip settings
- Only `skipNearestExpiryOnExpiryDay` has a block override (util/expirySkip.ts:23-26, 40-48). `skipNearestExpiryOnEve` is read from settings only (:8-14).

### F19 (LOW) Trading-day count ignores exchange holidays
- `tradingDaysToExpiry` counts Mon-Fri only (util/expiryOffset.ts:7-20, "NSE holidays ... are not subtracted"). Eve/expiry-day detection (util/expirySkip.ts:47) and the OTM step count (ant/AntContractMaster.ts:211) can be one off around a holiday: e.g. a holiday the day before expiry makes "eve" fall two trading weekdays out, so the eve rule does not fire. Documented in the source; listed so the feature line "handled" is not read as holiday-aware.
