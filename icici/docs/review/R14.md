## Findings

### 1. HIGH - Saving Admin > Strategy Configuration deletes the top-level `forecast:` block from config.yml

- Chain: `frontend/src/pages/AdminPage.tsx:558-575` (saveConfig -> `apiPost('/config', merged)`) -> `src/routes/admin.ts:94-107` (`nextConfig = configService.flatToConfig(flat)`, then `writeConfig(nextConfig)`) -> `src/prism/ConfigService.ts:119-123` (`flatToConfig` returns only `{ settings, strategies }`) and `ConfigService.ts:40-41` (`mergeIntoFile` returns the config untouched unless it is `this.config`, which a fresh `flatToConfig` object never is) -> `writeConfig` at line 66 dumps only those two keys.
- Reproduced safely: on a scratchpad copy of `config.yml` (`CONFIG_PATH` pointed at it), `configToFlat()` -> `flatToConfig()` -> `writeConfig()` produced a file with `strategies:` present and `forecast:` absent (`RESULT forecast kept: false strategies kept: true`). The real `config.yml` was not touched (`git status` unchanged for it).
- Failure scenario: the admin changes any field on the Strategy Configuration tab and presses Save. `config.yml` loses `forecast:` (config.yml:489 onward: `company.name`, `maxActiveContractors`, `sessionDays`, `orders.enabled`, filters, `dailyLimit`, ...). The file watcher hot-reloads the reduced config. I did not trace what each forecast consumer does when the block is absent; at minimum the owner's settings are silently gone, which also conflicts with the "never delete config.yml entries" rule. Any other future top-level key is lost the same way.
- Not covered by R01-R13 (R09 and R13 mention `forecast`/top-level keys only as read paths).
- Fix direction (not applied): `flatToConfig` should keep unknown top-level keys from the current config, or `writeConfig` should merge onto a fresh read for this path too.

### 2. MEDIUM - "Exit" in the acting-as banner cannot reach the server through Cloudflare (and not in the Vite dev proxy)

- `frontend/src/App.tsx:60` posts to `/act-as/stop`. `/act-as` is missing from `API_PREFIXES` in `cloudflare/_worker.js:3-8` and in `frontend/vite.config.ts:6-11` (the two lists are copies of each other). Every other URL the frontend calls is covered (checked by grepping all literal URLs in `frontend/src`).
- Failure scenario: admin uses "Use as" on a trader (`AdminPage.tsx` handleActAs), then clicks Exit on production. The POST goes to `env.ASSETS` (static) instead of the origin, the `catch` swallows the result (`App.tsx:60`), and `window.location.assign('/admin')` loads with the `actas` cookie still set (server `session.ts:77` keeps it up to 8 h). `/auth/me` still returns the trader (role `user`), so `RequireAdmin` redirects to `/`. The admin remains in a mode where "Orders you place are real" until the 8 h cookie expires or they use Logout. The server route itself is fine (`routes/auth.ts:134-140`).
- Severity medium because real orders are possible in the trader's account while the UI gives no working way out.

### 3. LOW-MEDIUM - Reloading or bookmarking `/admin/payouts/:id` shows raw JSON instead of the Pay page

- The worker forwards a multi-segment API-prefix path to the origin even for an HTML navigation (`cloudflare/_worker.js:13-14`: the page shortcut applies only when the path has no second `/`). On the origin, `GET /admin/payouts/:id` is the JSON API route (`routes/payouts.ts:137`, `requireAdmin`), which matches before the SPA catch-all (`server.ts:152`). The Vite dev proxy does the same for `/admin`.
- Failure scenario: admin refreshes the Pay page (or opens the link in a new tab) and sees the payout/payee JSON (admin only) instead of the page. Navigating inside the app works because `navigate()` is client-side.

### 4. LOW - Position cards are keyed by token + array index, not by token + broker

- `TradingPage.tsx:134` `key={`${trade.token}-${i}`}`; `PositionCard.tsx:13-14` keeps `targetPoints`/`slPoints` in local state. A position is identified by token + broker (`PositionCard.tsx:12`).
- Failure scenario (narrow): an account trading one contract on two brokers has two rows with the same token (`T-0`, `T-1`). If the server's broker order flips between SSE snapshots, the unsent target/stop-loss text stays with the index, so it moves to the other broker's row; "Set" then sends that row's `trade.broker` (`PositionCard.tsx:35`). For different tokens a list change remounts the card (key changes) and the typed value is simply lost.
- Related, unverified: `handleSquareOff` sends `trade.quantity` from the last SSE snapshot (`PositionCard.tsx:50`; the server takes `qty`, `routes/trading.ts:125-133`). I did not check whether the order process clamps it to the live holding if a strategy or target exit changed the quantity between snapshot and click.

### 5. MEDIUM-LOW - Shipped contract list (`symbols.txt`) is a month old and the build does not refresh it

- `frontend/public/symbols.txt` was last committed 2026-10-27 (file mtime Oct 22); `frontend/package.json:10` has `npm run symbols`, but `build`/`postbuild` do not run it, and `deploy-frontend.sh` just copies `public/`.
- Compared with a list generated now from `data/kite/NFO_instruments.csv` + `BFO_instruments.csv` using the script's own awk rule: 3852 current contracts are missing (28 of them NIFTY, for example `NIFTY_27250_CE`) and 1889 listed entries have no active listing any more.
- Failure scenario: Search & Buy (`OrderEntry.tsx:100-106`) and the Recommendation form (`RecommendPage.tsx:24`) offer expired contracts that the server then rejects, and cannot find newly listed strikes. Contractors' recommendations use the same list. Same root cause as the build-time snapshot design; nothing flags the staleness.

### 6. LOW-MEDIUM - Hard-coded lot sizes in `TradingContext.tsx:77-85` disagree with the instrument master

- Code: BANKNIFTY 15, FINNIFTY 25, SENSEX 20, everything else 65. Master (`data/kite/*_instruments.csv`, FUT rows): BANKNIFTY 30, FINNIFTY 60, NIFTY 65, SENSEX 20. Stock options (searchable in Search & Buy) all fall into the "65" default.
- Effect: `tradedLots` (line 83) is overcounted (for example 1 BANKNIFTY lot = 30 qty counts as 2 lots), so `isOrderDisabled` (line 85) can disable Flash and Search & Buy before the user's lot limit is reached. Client-side only (the server is the authority), but it blocks trading in the UI. `FlashSettingsModal.tsx:67` also hard-codes "65 for NIFTY".

### 7. LOW - Browser-local time zone used where IST is intended

- `DateRangeFilter.tsx:10-29` builds day/week/month ranges from the browser's local date (comment claims it avoids UTC problems, but non-IST browsers are still wrong). `AdminPage.tsx:47` documents "IST regardless of browser zone" and uses `istDay()` to filter open trades, but `openStrategyStatus` takes the closed-trades date from `resolveDateRange('day')` (browser-local, `AdminPage.tsx:173`), so the two halves of the Status modal can cover different days. `NiftyTicker.tsx:64` formats an epoch time with no `timeZone`, so the ticker time is wrong outside IST. (`MyTrades`, `Admin > Trades` and `Payments` use the same `DateRangeFilter`.)
- Failure scenario: owner travelling, or any non-IST browser: "This Day" is the browser's date, the ticker shows the browser's clock for an IST tick.

The same acting-as user hitting `/rules` or `/levels` ends there.

### 12. LOW - Join page: stale preview can show a PDF that does not match the details, and blob URLs are never revoked

In between, the user can tick the boxes against an agreement that does not match the form. Whether the accept endpoint binds to the shown PDF I did not verify.
- `URL.createObjectURL` (line 78) is never revoked (one blob per preview, per keystroke burst). Minor leak.
