## Findings

### 1. Short (SellToOpen) legs are not restored after a restart; their close books nothing (medium)
- `shortTrades` is filled only by `recordShortFill` (1191-1200) and nothing rebuilds it: `restoreOpenTradesFromMongo` selects only `action: 'Buy'` docs (1718), `loadContractFills` nets only Buy/Sell (2832). Grep shows no other writer of `shortTrades`.
- Scenario: a ButterflyStrategy short leg is open, the order process restarts (hot restart or crash). `shortTrades` is empty, so the 15:15 expiry force close and the drawdown-breach buy-to-close loops (orderProcess.ts:1728, 1792, which iterate `bookkeeping.shortTrades`) skip the leg; it stays a naked short at the broker. When the strategy later sends BuyToClose, `recordShortFill` finds no entry (1204-1207), logs a WARNING and drops it: no closed-trade row, no realized P&L, no drawdown input. `recordShortFill` also has no Mongo duplicate check (only the in-memory `processedFillIds`, 1178-1184).
- feature.md says "open positions restored from Mongo alone"; that holds for longs only.

### 2. ANT position list read is non-strict: a non-Ok reply reads as "everything flat" and closes tracked ANT positions at entry price (high)
- `readBrokerRows('ant')` calls `ANT.getInstance().getPositions()` without `{strict:true}` (bookkeeping.ts:1793). `ANT.getPositions` returns `[]` on any non-Ok envelope unless strict (ANT.ts:350-359; its own comment at 335-336 says this is exactly the "couldn't fetch read as no positions" hazard). `reconcileAntPositions` has the same read (1605-1606). The Prism read is strict (1814) and Kite/Breeze fail closed on a non-array.
- Scenario: at the 15:45 EOD sync, `npm run sync` or POST /reconcile the ANT session is invalid or the endpoint answers a non-Ok status. `readBrokerRows` returns `[]` (not null). In `syncExternalCloses` every tracked ANT trade has `heldOf(rows)===0` (1981), the 3 s confirmation read returns `[]` again (2003-2006), `impliedExternalSell` finds no row ltp and falls to "ESTIMATED at the entry price (no P&L)" (1893-1894), and `bookExternalSell` closes each trade with a `BROKER-SYNC-` id, removing it from memory and the exit monitor (2049, 1399-1402) while the broker still holds it. The only guard, `mongoOpenQuantity` (2029), blocks a second close but not a first one. The strategies' reconcile then also sees the leg as closed. Zero P&L is booked, so the loss is also hidden from the daily/weekly drawdown.
- Fix direction: use the strict read in `readBrokerRows` and in `reconcileAntPositions`.

### 3. Restore uses only the newest lot's target, stop, GTT id, entry time (medium)
- In `restoreOpenTradesForTsym`, `row = rows[0]` is the newest remaining lot (2928-2929) and `targetPrice, stopLossPrice, gttTriggerId, antOrderNo, product, strategy, entryTime` are copied from it only (2967-2974). `extraGttTriggerIds` is never restored (live merge keeps them, 1336-1339).
- Scenario: two Kite lots bought separately, each with its own GTT; restart. Only the newest lot's GTT id is tracked; the older GTT stays live at Kite with nothing that will ever delete it. Kite GTT sells bypass the never-short guard (comment 1391-1392), so after the position is closed by another path the orphan GTT can trigger and sell a flat account short. Stops/targets are measured from the newest lot's entry rather than the blended price.
- `entryTime` of the restored trade is the newest lot's, not the earliest. `foreignShortfalls` uses `min(entryTime)-5 s` as the "lots exist from" bound (2155-2156), so a non-platform sell between the first and the newest lot is excluded from attribution; closed rows also carry the newest lot's entry time.

### 4. Trades dropped or cut in memory without releasing their GTT (medium)
- The normal Sell path deletes the position's GTTs (1393-1398). Two other paths shrink or remove a tracked trade without that: `syncExternalCloses` "Mongo already shows closed" branch (2034-2043: splice + exit-monitor unregister only) and `attributeByOrderIds` (2639-2648: splice, or `t.quantity -= cut`, no GTT delete, no exit-monitor/GTT resize).
- Scenario: attribution reduces a Kite trade from 195 to 130; its GTT is still sized for 195 and, when it fires, sells 65 more than the user holds (GTTs bypass the guard). For a whole-trade drop the GTT is left live.

### 5. Live average cost vs FIFO lots: P&L and stop basis change across a restart (medium)
- Live bookkeeping merges buys into one weighted-average row and books sells against that average (1329-1333, 1367). Restore (2926-2938), the "already closed?" check (1948), `repairClosedTradesFromFills` (2699, `pairFillsFifo`) and `attributeByOrderIds` all use FIFO lots.
- Scenario: buys 100 @100 then 100 @120 (live average 110); sell 100 @115 books +500. After a restart the remaining 100 are restored as the second lot @120 (not @110); selling it @115 books -500 instead of +500, and the stop is built on 120. `repairClosedTradesFromFills` would price the first sell at 100 (+1500), so a repaired row and the live row disagree (the 5-minute / quantity match in 2715-2721 only prevents a duplicate, not the mismatch). The only compensation is the broker-average cross-check (2992-2997), which runs only for a broker-driven restore with a single owner holding the whole broker position; the Mongo-only restore (`brokerQuantity === null`, 2982) has none.

### 6. Investment, capital and lot gates test "already at cap", not "this order would exceed it" (medium)
- `currentInvestment >= maxInvestment` (946-953, 980) and `capitalLeft > 0` (961-966) never add the order's `estimatedOrderValue`; only the optional per-order cap compares it (983-986), and `estimatedValue` is 0 for buyIndex/antBuyIndex (see the PendingOrder comment 133-137).
- Scenario: account capital 200000, 199000 in use, a manual or strategy buy of an explicit 150000 passes and the account ends at 349000. Strategies that size with `resolveMaxInvestmentQuantity` (449-455) are safe; fixed-quantity paths are not. The code comments call this a "ratchet"; feature.md presents it as a cap.

### 7. Durable state is removed before the follow-up action; several writes are fire-and-forget (medium)
- Locked sell: when a resting locked sell is cancelled, the tracker untracks it (and deletes its `pendingXxxLimitOrders` row) before telling listeners (pendingOrderTracker.ts:292-295), then `onLockedSellCancelled` deletes the `lockedSells` row (lockedSells.ts:63) before the re-placement (lockedSells.ts:73-80) and only after it re-records (lockedSells.ts:74). Scenario: a crash or restart between the delete and the re-placement leaves no ledger row and no tracked order: the locked-price sell is never re-placed ("a locked sell that is cancelled leaves the position unmanaged" is the very risk the module exists for). The re-placement itself can be placed at the broker and the process die before `recordLockedSells` persists it, leaving a live untracked order.
- `tracker.track` and `recordOrderOwner` persist without awaiting (pendingOrderTracker.ts:130-135, orderOwners.ts:30-45) and are not part of `drainPendingWrites` (3132-3139). A stop right after a limit order placement can lose the tracker row, so a later fill is not booked (the 2026-09-01 incident class).
- Filled locked sells are never `forget`-ten (only the cancel path calls it); rows live until day rollover (lockedSells.ts:36-40). Harmless today, but `isLockedSell` then answers true for a filled order.

### 8. `withSellLock` has no wait bound and keys per user (medium-low)
- BrokerExecutor.ts:12-27: the next sell for a (broker, user, contract) awaits the previous one's promise with no timeout, unlike Kite's own lock (45 s then refuse, Kite.ts:289-311). If one broker call hangs (bookkeeping.ts:79-88 states the Breeze SDK has no HTTP timeout; whether every executor bounds its place call was not verified), every later sell of that contract for that user, including a stop-loss or the 15:15 force close, queues behind it indefinitely.
- The key includes `userId`, but net positions are per broker account. Two users' strategies selling the same contract on one account (the 2026-11-18 case) are not serialized; an in-flight sell of one is invisible to the other's guard (only tracked resting orders count in `restingSells`, pendingOrderTracker.ts:101-107). feature.md states the key as (broker,user,contract), so the code matches the line, but the race the lock was written for remains across users.

### 9. A throwing fill listener skips the remaining listeners and fails the caller after booking (low-medium)
- `for (const l of this.fillListeners) l(...)` (1164) has no try/catch (compare the isolated loop in pendingOrderTracker.ts:285-291). The position is already booked at that point.
- Scenario: listener 1 throws on a fill; listeners 2..n (strategy notification over IPC) never run. The tracker's `bookFill` rejects, the order stays tracked, the next poll's `recordFill` returns early as a duplicate (1121-1124) and untracks it. The strategy never hears of the fill.
- The same applies to `notifyPositionsChanged` listeners (231-233).

### 10. No finite/positive check on booked price and quantity; NaN and 0 slip through (low-medium)
- `recordFill` accepts any `price`/`quantity`. `updateTradeFromPrismMessage` builds them with `parseInt`/`parseFloat` of broker fields (1263-1265): an `undefined` avgprc gives NaN. A NaN entry price poisons the aggregate average (1333) and every later P&L (`userPnL`, `closedTrades`), and `getCurrentInvestment` becomes NaN so `currentInvestment >= maxInvestment` is false and the gate opens (946, 980).
- `drawdownDecision` guards only `pnl === null` (percentConfig.ts:73-77); `NaN <= -limit` is false, so a NaN total returns `'ok'` instead of `'unknown'`. `getRealizedPnLSince` sanitises Mongo rows with `|| 0` (629) but adds held rows' `realizedPnL` unsanitised (628).
- Kite's tracker adapter sets `bookAtAnyPrice` (pendingLimitOrders.ts:32), so a COMPLETE with no usable price books at price 0 (pendingOrderTracker.ts:276-282, ALERT only): the average falls, `getCurrentInvestment` understates, and the later exit's P&L is inflated, which feeds the max-profit latch.

### 11. Dedupe and ownership are keyed by broker order id alone (low)
- `processedFillIds` (1121), `fillAlreadyStored` (`brokerOrderId`+`action` only, 1102), the unique `orderOwners` index on `orderId` (orderOwners.ts:94) and `collapseFillsByOrderId` (fillNetting.ts:43-55) never include the broker. Two brokers issuing the same id string (Kite ids are bare numerics, Prism/ANT ids are numerics too) would make the second broker's fill "already processed"/"owned by the other user" and drop it. Not seen live; unverified whether the id spaces can overlap.
- `bookExternalSell` ids are `BROKER-SYNC-<broker>-<tsym>-<Date.now()>` (1960): two users' closes of the same contract inside one millisecond would share an id; first-writer-wins would then attribute both to the first user and `collapseFillsByOrderId` would drop the second user's Sell, leaving his position phantom-open after a restart. Very unlikely (sequential awaits), noted for completeness.

### 12. Process-lifetime accumulators never reset at the day rollover (low)
- `userPnL` (176) and `notifiedThresholds` (198) have no reset (grep over `src/` finds none) and are not rebuilt on restart (`loadClosedTradesFromMongo` reloads rows only, 1461-1491). `checkDrawdownNotification` (1017-1038) therefore compares a multi-day cumulative P&L to the per-session loss limit, and the 80%/100% warnings fire once per process lifetime. `/users` `sessionPnL` (routes/users.ts:35) shows the same cumulative figure. The drawdown BLOCK is correct (it reads `closedTrades` by day/week); only the notifications and the displayed figure are affected.

### 13. `brokerCapOverride` is an in-memory runtime control (low)
- 278-283: the BulkPcr loss-trip cap cut lives only in a Map. CLAUDE.md forbids in-memory-only operator controls; a restart later the same day restores the configured cap. Whether the strategy re-sends the cut after its own restart was not checked.

### 14. Resting-buy reservations are not rebuilt after a restart; broker-less reservations are excluded from per-broker sums (low)
- `pendingOrders` is in memory (177) and `PendingOrderTracker.loadFromMongo` restores the order but not a reservation (pendingOrderTracker.ts:164-170). After a restart, resting limit buys hold no headroom until they fill, so a new buy can pass the cap and the later fill overshoots it.
- Comment at 138-143 says a reservation with no broker counts as "any broker"; the filters (`p.broker === broker`, 571-585) exclude it. Currently `resolveRequestBroker` always returns a string, so this is latent.

### 15. `recordFill` yields before booking, so a Sell can be booked ahead of its Buy (low)
- Between the id claim and `_processTradeEvent` there are awaits (the in-flight insert wait up to 5 s, then the Mongo lookup: 1131-1135). A Sell for the same contract that arrives right after a Buy but is faster through its own lookup finds no open position (1408-1416): it stores the raw doc and runs `repairClosedTradesFromFills`, which writes a closed row from the fills but does not touch `trades`. The Buy then books as open: a phantom open lot of the full quantity that persists until the sync or a restart (the restart would net it correctly from Mongo).
- Executors normally await the Buy before selling, so this needs two near-simultaneous deliveries (poller plus exit path).

### 16. A swallowed raw-fill insert failure loses the fill for restart (medium)
- The raw `Trade` insert is fire-and-forget with only a log on failure (1305-1307); `failedBookingFillIds` covers throws, not a failed insert, and nothing retries it. Restart restores from Mongo alone (1712).
- Scenario: Mongo hiccups during a Buy fill. Memory is right, Mongo has no Buy. After a restart the position is not restored (no exit monitor, no GTT tracking, strategy sees it flat); the sync only reports it as `brokerExcess` (1527-1530, 2569-2571) and never books a Buy. A lost Sell doc does the opposite: a closed position is restored as open.

### 17. Drawdown and lot gates fail open until user limits load (low)
- `drawdownState` returns `'ok'` when `accountCapital` is not cached (671-672). Startup logs "continuing with defaults" if `loadUserLimits` fails (orderProcess.ts:1661) and `loadDrawdownLatches` is started without await (orderProcess.ts:1752). In that window a real user's buys are gated only by the default lot limit/`maxInvestment`, and a latched daily breach is not seen until the latch read returns. The realized-P&L check still applies for users that have capital cached.

### 18. Lot-limit mode counts lots with a name-based lot size (low)
- `getTradedLots` divides by `getInstrumentLotSize(tsym)` (457-461), which knows only BANKNIFTY/FINNIFTY/SENSEX and otherwise uses the NIFTY size (365-370). Stock options (TopStock strategies trade them) and any index whose lot size changed are miscounted, so a lotCount-mode user's limit is applied to the wrong number of lots. The comment at 359-364 already says it is a fallback.

### 19. `eodRepairBroker` assumes the restore makes memory equal Mongo; `mergeRestored` only adds (low)
- 2759 comment: "memory must equal Mongo before it is compared with the broker". `mergeRestored` skips an existing (user, token, broker) row (1550-1553), it never corrects its quantity or price; a restored row with an empty token (`row.token ?? brokerToken ?? ''`, 2951) matches any other empty-token trade of that user and broker, so a second restored contract can be refused as a "duplicate". The EOD comparison therefore runs against stale memory in those cases.

### 20. scripts/repair-closed-trades.js (low)
- Connects to a hard-coded `mongodb://localhost:27017/stocks` (script line ~105) instead of the app's configured URI; keys contracts without expiry (`keyOf`) and relies on the quantity-equality skip to avoid conflating two expiries; rewrites `realizedPnL` after the fact without touching the in-memory `closedTrades`, `userPnL` or an already-persisted daily drawdown latch (a day latched on the old, wrong P&L stays latched). The file's header documents the restart requirement for memory; the latch is not mentioned.

## Notes on verified-OK items (no finding)

- The drawdown latch is written before the breach listeners run and restored at startup (780-799); weekly closure sets the cache flag synchronously and retries the Mongo write (847-858); `updateUserSettings` does not re-open a freshly closed account (251-254).

- Tests exist for dedup, race, short fill and insert rejection (src/test/bookkeeping*.test.ts); not run (report-only).
