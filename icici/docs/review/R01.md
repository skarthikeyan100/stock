## Findings

### 1. Loopback bypasses BOTH authentication and CSRF (drive-by from a browser on the host) - medium
- Code: `requireCsrfHeader` returns early for loopback (session.ts:12-13); `requireAuth/Admin/SelfOrAdmin` skip entirely for loopback (session.ts:168-196); the global CSRF middleware is in server.ts:92-98. The server also has no Host-header check.
- Scenario: the trader's browser runs on this machine. Any web page he visits can submit a `application/x-www-form-urlencoded` form POST (no preflight, `bodyParser.urlencoded` accepts it) to `http://localhost:3000/...` (or rebind a DNS name to 127.0.0.1). The request arrives from 127.0.0.1, so there is no cookie and no `X-Requested-With` requirement: the route handler runs as if it were an admin. Reachable state-changing admin routes include `/config`, `/reconcile`, `/sync`, `/strategies/*`, `/order/*`.
- Note: the auth bypass for ops scripts is the user's explicit instruction (session.ts:109-112). The CSRF exemption is a separate, additional hole that makes the bypass reachable from the web. A cheap mitigation that keeps the scripts working would be to require a custom header (e.g. a fixed `X-Requested-With`) from the scripts, or to reject loopback requests whose `Host`/`Origin` is not localhost/127.0.0.1.

### 2. Mock mode claims are not supported by the current process model - medium
- `MOCK_QUOTES`/`MOCK_DATE`/`MOCK_BROKER` are read only in constants.ts:44-46; `MockAPI` is used only by `src/prism/RestAPI.ts` (the legacy Shoonya REST path) and a few strategy gates (`if (MOCK_BROKER) return ...`). Nothing in `src/processes/**`, `src/ant`, `src/kite`, `src/breeze` or the orchestrator reads them. `config.mock.yml` is referenced only by package.json:15-16.
- `npm run server:mock` (package.json:15) starts only `dist/server.js` (the frontend) on PORT 3001. It does not set `ORDER_IPC_SOCKET`/`STRATEGIES_IPC_SOCKET`/`DATA_IPC_SOCKET`, so it connects to the LIVE sockets at /tmp/icici-*.sock if the live system is running. With loopback auth bypass (finding 1) a mock instance can send real order/strategy/config-sync requests to the live trading process. It also still binds ports 80/443 (server.ts:213, 223), colliding with a live frontend (logged only).
- RUN_MOCK_MODE.md step 3 calls `/connect`; no such route exists (only `/ant/connect`). The feature line "Mock mode" therefore describes something that cannot run end to end.

### 3. Hot-restart watch lists miss modules each child really loads - medium
Checked against the compiled `require` graph (dist/).
- `trading` (orchestrator.ts:289-295) does not watch: `dist/broker/` (brokerClients.js, BrokerClient.js), `dist/prism.js`, `dist/levelLimits.js`, `dist/levelRules.js`, `dist/user.js`.
- `frontend` (orchestrator.ts:304-311) does not watch the OrderClient (`processes/strategies/OrderClient.js`, its IPC client), `dist/broker/`, `dist/prism.js`, and imports `strategy/*`, `processes/order/*` and `processes/strategies/*` modules (via route code) that are unwatched.
- Scenario: a fix to `src/broker/brokerClients.ts` or `src/user.ts` is compiled and nothing restarts `trading`; the operator believes the fix is live while the old code keeps running (and the next real restart silently changes behavior). Conversely shared-dir changes restart both children even when only one uses them (harmless).

### 4. A code change suppressed during market hours is never applied afterwards - low/medium
- orchestrator.ts:197 updates the stored snapshot (`snapshots.set`) BEFORE the market-hours gate (:203). After the gate says "NOT restarting", the new hash is already the baseline, so no later event re-evaluates it.
- Scenario: a fix compiled at 11:00 is skipped by design; after 15:35 nothing restarts the child. The orchestrator log said "restart by hand", but the next unrelated edit will restart it (applying both changes at once), or none will. Keeping the old snapshot (or a "pending change" flag re-checked on a timer) would apply it when the window opens.

### 5. Shutdown can orphan a child spawned mid-restart - low/medium
- `shutdown()` (orchestrator.ts:319-325) stops `liveChildren` as they are at that instant, then `process.exit(0)`. `Role.restart` (orchestrator.ts:249-254) runs `stopChild(old)` then `role.start()` with no `shuttingDown` check, and `spawnChild` does not check it either.
- Scenario: SIGTERM/Ctrl+C arrives while a hot restart is waiting for the old `trading` to exit (up to 5 s). The old child dies, `role.start()` then spawns a new `trading` (a live-order process) after `shutdown` already took its snapshot; the orchestrator exits, leaving an orphan holding the sockets and broker sessions. The next `npm run processes` stale-killer only matches `dist/orchestrator.js`, so the orphan is not killed.

### 6. Crash handling: "alert" is log-only; crash loops never give up - low
- A data crash prints `ALERT:` to the log (orchestrator.ts:282-285); nothing else (no Mongo/notification/mail). It depends on someone tailing orchestrator.log (the monitor scripts do).
- `MAX_FAILED_RESTARTS` (orchestrator.ts:107, 126-137) counts only restarts that failed to spawn. A child that spawns and exits immediately every time (e.g. `verifyMasterFiles()` throwing at start, orderProcess.ts:1651) is "started" each time and resets `failedRestarts` to 0, so it respawns every 30 s forever, re-running startup against the brokers each time.

### 7. Cloudflare front door gaps - low
- `cloudflare/_worker.js:3-7` prefixes omit `/sync` and `/strategyPnl`, both real admin routes (admin.ts:79, trading.ts:205). Via the public site they are served by the Pages asset handler (404/SPA), so feature.md's "POST /sync" works only locally (the frontend does not call either; I found no use in `frontend/src`).
- `CF_ORIGIN_SECRET` is optional and is not in `.env.example`. With it unset (default), `cloudflareOnly` (cloudflareOnly.ts:50-60) admits any request from ANY Cloudflare zone, not only this one; auth still applies to non-demo routes. `clientIp()` (streams.ts:132-137) trusts `CF-Connecting-IP` for any non-loopback peer, so such a caller can rotate it to defeat the per-IP demo limits (the global caps in streams.ts:107-111 and :140 still hold).
- The CIDR list is hard-coded "as of 2026-09-03" (cloudflareOnly.ts:6-7); a new Cloudflare range would be blocked (403) until edited.

### 8. `/demo/subscribe` is a state-changing GET, outside the CSRF guard - low
- streams.ts:146 is `router.get` and subscribes/unsubscribes feed tokens (via StrategiesClient). session.ts:8-10 states state-changing routes are POST-only. Anonymous and cross-site callable, but bounded (20 tokens, per-IP 30/min, allow-listed tokens). Effect limited to feed subscription churn.

### 9. A throwing tick handler starves later handlers and is logged as a parse error - low
- DataLink.ts:56 loops `for (const h of this.tickHandlers) h(tick)` with no try/catch; the surrounding `readJsonLines` catch (jsonLines.ts:20-26) reports any throw as "Failed to parse a tick" and prints the whole tick line. In `trading` the handlers are async wrappers (safe); in `frontend` the server.ts:171-185 handler and the forecast engine handler are synchronous, so a throw there (e.g. a malformed quote) skips every handler registered after it for that tick and floods the log.
- `DataServer.broadcast` (DataServer.ts:63-75) drops ticks to a client more than 32 MB behind, logging at most once per 10 s, and gives that client no marker; it then continues with a gap in the stream and stale prices.

### 10. Streams: un-coalesced position fan-out; notification poll window - low
- streams.ts:257-265: every `positionsChanged` triggers its own full `orderClient.stats()` and a push to all clients. Bursts of fills issue concurrent `stats()` calls; if replies are processed out of order, an older snapshot can be the last one a client receives until the next change. Not coalesced or sequenced.
- streams.ts:337: `lastNotificationPollAt` advances before the query; if the query throws, the next window starts at "now - 5 s", so documents created during a longer Mongo outage are never pushed on the stream (they remain available via the GET endpoint). Documents created while no client is connected are likewise skipped (streams.ts:338).

### 11. Frontend jobs are timer-only, first run after one hour - low
- server.ts:199-202: `setInterval` hourly, no run at start. The frontend is restarted by the orchestrator on any dist change in its watch list; each restart resets the 60-minute timer, so on an active development day the invoice reminder / agreement jobs may not run for hours. Also, a second frontend instance (`npm run server` alongside the orchestrator) would run the same jobs twice; `runInvoiceCheck` (invoiceRule.ts:55-75) re-closes an account that an admin reopened while its payout stays `pending` (checks `accountClosed !== true` every hour).

### 12. Socket servers: no `error` handler, unconditional unlink, serving during drain - low
- orderProcess.ts:1808, strategiesProcess.ts:413 and DataServer.ts:35 unlink an existing socket path unconditionally before listening. A second instance (e.g. an orchestrator started without the stale-killer, or a standalone `node dist/processes/orderProcess.js`) silently removes the live process's socket; the live process keeps running with no reachable endpoint. None of the three `net.Server`s has an `'error'` listener (listen failures become uncaught exceptions; the strategies/trading/frontend handlers keep the process alive in a socketless state, while `data` exits).
- tradingProcess.ts:25-31: on SIGTERM it unlinks the sockets and drains writes (up to 3.5 s, bookkeeping.ts:3132) but keeps handling ticks and order requests until exit; an entry placed in that window is lost from a process that is about to die (the next start restores from Mongo, which the fill may not have reached).

### 13. feature.md wording errors found while verifying - low
- Line "Per-process IPv4-only DNS override for Kite/ANT hosts (Breeze needs IPv6)": the code forces Breeze's host to IPv4 (kiteDns.ts:41-44, change dated 2026-10-19); the header comments in orchestrator.ts:16-24 and server.ts still say Breeze needs IPv6.
- `jsonLines.ts:3-5` header still mentions the retired stdio pipes (comment only).
